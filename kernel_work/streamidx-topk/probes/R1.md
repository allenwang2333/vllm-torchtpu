## VERDICT

**Option A drops to rank 4 — but the demotion is conditional on `bkv_p`, and that condition is the
most useful thing this probe found.**

The gate is not a property of Option A. It is a function of how many DMAs are in flight:

| DMAs in flight | `bkv_p` | time saved by halving the record | gate ("> 33 % survives") |
| ---: | ---: | ---: | --- |
| 8 | **2** — today's nightly decode | **21.0 %** | **fails** |
| 12 | **3** — Candidate 0's measured win, and the doc's stated composition | **25.4 %** | **fails** |
| 16 | 4 | 32.0 % | fails, marginally |
| 24 | 6 | **42.7 %** | **passes** |

*(grid 128, `indirect` form, best-of-9. The grid-16 nightly-exact pass gives 20.5 / 24.8 / 30.4 /
40.4 % — the same shape.)*

**At every configuration the design proposes to ship, Option A fails.** §4's composition plan is
"take A **and** Candidate 0", and Candidate 0's measured `bkv_p` is 3, where halving the record
saves 25.4 %. So the ranking the doc should record is the one Flip 1 wrote down:
**`Candidate 0 > C > B > A`.**

**But "A is descriptor-bound" is the wrong lesson.** The reason the byte reduction is wasted at
`bkv_p = 2` is that *neither* record is anywhere near the HBM roof there — the DMA stream is limited
by descriptor issue, and shrinking the payload of a transfer that is not paying for its payload buys
nothing. Raise the concurrency and the roof starts to bind: at 24 in flight the 262 KiB arm reaches
**3.335e12 B/s, 99.6 % of the 3.347e12 P6 measured for a fully contiguous read**, and from there the
byte reduction pays almost in full (42.7 % against a 49.6 % ideal). **A and Candidate 0 are
complementary, not competing** — A is worth revisiting if and only if Candidate 0 lands above
`bkv_p ≈ 5`.

**The absolute stake never reaches the doc's predicted band under any configuration measured.** At
the nightly geometry the saving is 15.2 µs at `bkv_p=2`, 17.8 at 3, 20.3 at 4 and 26.4 at 6, against
a 221.4 µs decode call for which the doc's own −13 % to −22 % prediction required **28.4–49.4 µs**.
This is the sturdiest finding here: it survives every reading of the gate, and it holds across the
whole concurrency sweep.

**What Flip 1 got right and wrong.** It named "descriptor issue **and** address indirection".
Descriptor issue is exactly the mechanism, established model-free below. Address indirection is
**free** — a scalar-prefetch page table plus both `min()`/`max()` clamps cost 0.2–1.0 %, and a
runtime-clamped extent costs nothing. **P6's charging rule is not defeated by indirection.**

**Two alternative explanations were tested and neither survives**, which is what licenses the above:

- **Alignment is not it.** Option A's 258-row page gives a 132,096 B stride ≡ 1024 mod 4096, so
  three of every four DMAs start 4 KiB-misaligned, while every incumbent DMA is 256 KiB-aligned. A
  264-row control page (135,168 B ≡ 0 mod 4096, 2.33 % more bytes) is **slower, by exactly the
  amount its extra bytes cost** — predicted 442.87 µs from the pair's own marginal byte rate,
  measured 442.69 µs, a 0.04 % discrepancy. Misalignment costs nothing measurable. §3.
- **Dispatch contamination is not it.** §5.

## 1. What ran

Every arm holds the **DMA count, the grid, the pipeline depth and the number of in-flight DMAs
fixed**, and changes only the shape of the record each DMA moves.

| | rec 256 (incumbent) | rec 132 (Option A) | rec 135 (aligned control) |
| --- | --- | --- | --- |
| `cache_kv` | `u8[2048, 256, 4, 256]` | `u8[2048, 258, 4, 128]` | `u8[2048, 264, 4, 128]` |
| bytes per page DMA | **262,144** | **132,096** | **135,168** |
| page stride mod 4096 | 0 (aligned) | **1024 (misaligned)** | 0 (aligned) |
| source footprint | 536.87 MB | 270.53 MB | 276.82 MB |

`258 × 4 × 128 = 132,096` is Option A's layout as §3.1 specifies it (1024 payload rows + 8 scale
rows = 1032 rows of 128 B; `1032/4 = 258`), and it is the extent §3.1's file plan gives for
`_fetch_bkv`.

Three **forms** of offset arithmetic, so the indirection cost is isolated rather than assumed:

| form | what it is |
| --- | --- |
| **`indirect`** | byte-for-byte `_fetch_bkv`: `page_idx = min(page_indices_offset + i, num_page_indices - 1)`, `safe_page_offset = min(page_indices_ref[page_idx] * psp, max(0, max_hbm_pages - psp))`, page table in scalar prefetch. **This is the arm R1 is about.** |
| `affine` | the same DMAs at an offset computed affinely from `program_id`; no page table, no data-dependent clamp. P6's form at `_fetch_bkv`'s geometry. |
| `indirect_dynlen` | `indirect` plus a runtime-clamped **extent** (`jnp.minimum`) on both slices, in `_fetch_bq`'s idiom. See §6 — this is *not* what `_fetch_bkv` does, and the arm exists to prove the distinction does not matter. |

**Geometry** is nightly decode (`measurement_and_design.md` §Area 2, line 429): grid `(16,)`,
`seq_batch_size = 4`, `bkv_p = 2`, `num_bkv = 5` → **640 DMAs × 262,144 B = 167.77 MB per call**,
the doc's own decode figure to the byte. Two grids: `--num-grid 128` (that schedule repeated 8×, so
both arms sit far above the host dispatch floor — **this is the pass of record**) and `--num-grid
16` (the nightly call exactly). `bkv_p` ∈ {2,3,4,6} → {8,12,16,24} DMAs in flight; 3, 4 and 6 all
fetch 12 pages per sequence, so the concurrency sweep varies in-flight depth at a **constant byte
count and constant DMA count** (6144 at grid 128).

The DMA schedule is a transcription of `_fetch_bkv`'s: same double-buffered start/wait, same
per-(batch, page) descriptor, same self-copy wait idiom, same `SemaphoreType.DMA` array, same
`disable_bounds_checks=True`, same VMEM double-buffer shape. There is deliberately **no consumer**
of the fetched bytes, exactly as in P6.

### 2.1 The gate's three readings, and why they do not matter here

§5's R1 row is internally inconsistent, and the inconsistency is worth pinning down precisely rather
than quietly resolving in the convenient direction:

1. **Literal text.** "If the charge ratio is ≥1.5 … A drops to rank 4." Under this probe's
   definition `charge_ratio = t256/t132`, the measured 1.266 is **below** 1.5, so *the literal
   inequality does not fire.* It cannot be the intended reading — under this definition 1.0 means
   "descriptor-bound, A dies" and 2.0 means "byte-proportional, A wins", so `≥1.5` is the *passing*
   direction — but the doc says what it says, and quoting "1.265 ≤ 1.5 → fails" against a gate whose
   text reads `≥ 1.5` silently reverses it. The threshold value is right; the inequality is
   backwards. **Doc fix required.**
2. **The parenthetical**, "saves ≤33 % of the time", which is coherent and is what this report
   applies. It corresponds to `charge_ratio ≤ 1.4993`.
3. **P6's definition**, `charge = time_ratio / byte_ratio`, where 1.00 is perfect
   byte-proportionality; here `≥1.5` really is the failing direction. But **this is a different
   test**: P6-style ≥1.5 ⟺ saved ≤ 24.4 %, not ≤ 33.3 %. Conversely saved ≤33.3 % ⟺ P6-style ≥1.323.

The three readings would disagree at `bkv_p = 3` (P6-style 1.481 < 1.5 passes; 25.4 % ≤ 33.3 %
fails). They do **not** disagree about the shape of the answer: under all of readings 2 and 3, the
saving is far short at `bkv_p` 2 and 3 and comfortably sufficient at `bkv_p` 6. Nothing in the
verdict rests on picking between them.

### 2.2 The mechanism: descriptor issue, which is what Flip 1 named first

Flip 1's hypothesis was that the DMA's cost is set by "descriptor issue **and** address
indirection". These are separable and the data separates them.

**Address indirection is free.** `measured`, at fixed record size:

| | grid 128 (`j-3e588eaa`) | grid 16 (`j-3e588eaa`) | grid 128 (`j-b0e33be2`) |
| --- | ---: | ---: | ---: |
| `indirect / affine` at rec 256 | 1.002 | 1.007 | 1.005 |
| `indirect / affine` at rec 132 | 1.007 | 1.003 | 1.009 |
| `indirect_dynlen / indirect` at rec 256 | — | — | 0.999 |

The page-table lookup and both clamps cost **0.2–1.0 %**; a runtime-clamped extent costs nothing.
Note also that `affine` at rec 256 saves only 21.4 %, so **P6's own form, re-measured at
`_fetch_bkv`'s geometry, fails the gate too** — the difference from P6 is the transfer geometry, not
the addressing.

**Descriptor issue is the whole of it, and this is model-free.** `derived` from the arm times, one
division each:

| ns per DMA | 8 in flight | 12 | 16 | 24 |
| --- | ---: | ---: | ---: | ---: |
| rec 256 (grid 128) | 108.8 | 88.0 | 81.0 | **78.6** |
| rec 132 (grid 128) | 86.0 | 65.7 | 55.1 | **45.1** |

At a **fixed record size**, raising in-flight depth from 8 to 24 cuts per-DMA time by 28 % (rec 256)
and 48 % (rec 132). Nothing about the bytes changed. That is a size-independent per-transfer cost
being hidden by concurrency, which is descriptor issue. In the `main` job the same thing shows up as
an even cleaner signature: going 8 → 12 in flight removes **20.7 ns/DMA at rec 256 and 20.4 ns/DMA
at rec 132** — the *same absolute nanoseconds* at both record sizes.

**And the two arms saturate at different points, which is the whole answer.** rec 256 flattens
between 16 and 24 in flight (81.0 → 78.6 ns, 3 % for 50 % more concurrency) because it has arrived:
3.335e12 B/s is **99.6 % of the 3.347e12 P6 measured for a contiguous read**. rec 132 is still
falling steeply at 24 (55.1 → 45.1 ns, 18 %) and reaches only 2.932e12, 87.6 % of the same roof —
half-size records need more of them in flight to cover the same issue cost. So:

> The byte reduction is worth what the stream is short of the roof. At `bkv_p = 2` the incumbent is
> at 72 % of the roof and the saving is 21 %; at `bkv_p = 6` it is at 99.6 % and the saving is 43 %.

### 2.3 The two-term fit, and what it does *not* say

A `t = n × (a + b × bytes)` fit gives a marginal rate of 5.4–5.8e12 B/s, stable across both jobs,
both grids and every `bkv_p`, with the intercept `a` falling from ~63 ns/DMA at `bkv_p=2` to
~43 ns at 3. Constant slope with a shrinking intercept is the same story as §2.2.

**The marginal rate is not an anomaly and is not evidence of elision** — an earlier draft of this
report said it was, wrongly, and the correction is worth stating. It is a difference quotient
between two arms, not a rate: it exceeds `1/BW` exactly when the two arms do not share an intercept,
which is the finding, not a contradiction of it. Every arm's *absolute* bandwidth is below every
candidate roof. And the 3.70e12 it was being compared against is `7.40e12 // 2`
(`hardware-facts.md:34`), a per-core half of a chip-shared resource, so it is not obviously the
applicable ceiling for a single core's difference quotient anyway. **The fixed cost is quoted only
as a trend, never as a value**, because the shared-intercept assumption is the thing that fails.

## 3. Alignment: tested, and it is not the explanation

Option A's 258-row page has a 132,096 B stride ≡ **1024 mod 4096**, so three of every four DMAs
start 4 KiB-misaligned; every incumbent DMA starts 256 KiB-aligned. P6 never exercised this — its
source had power-of-two row strides. If misalignment were costing real time, part of the residual
would be a property of *the packing Option A happens to specify* rather than of the byte reduction,
and A should be re-specified with a padded page instead of demoted. This was the strongest untested
alternative explanation, so it got a control arm: **rec 135**, a 264-row page whose 135,168 B stride
is ≡ 0 mod 4096, for 2.33 % more bytes.

`measured (j-3e588eaa)`, grid 128, `indirect`:

| `bkv_p` | t(132,096 B, misaligned) | t(135,168 B, aligned) | measured ratio | **byte-model prediction for the aligned arm** | discrepancy |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 2 | 440.11 µs | 442.69 µs | 1.0059 | **442.87 µs** | **−0.04 %** |
| 3 | 403.62 µs | 406.31 µs | 1.0067 | **406.86 µs** | **−0.13 %** |

The prediction takes the marginal byte rate implied by that same `bkv_p`'s own 256/132 pair and
charges the aligned page's extra 3,072 B/DMA at it. The aligned arm is **slower**, and slower by
almost exactly what its extra bytes cost — within 0.13 %. At grid 16 the aligned arm comes out
0.5–1.0 % *above* the byte-model prediction, i.e. if anything alignment is very slightly
unfavourable there.

**Misalignment costs nothing measurable. Option A's residual is not an alignment artifact, and
padding the page to 264 rows would not rescue it** — it would cost 2.3 % more bytes for no return.

## 4. What this means for Option A

Option A is a **movement-only** change: §3.1 is explicit that it is bit-identical, moves no work
between units, and changes only how many bytes cross HBM. Its predicted win is therefore bounded
above by the DMA-stream saving measured here.

| | `modelled`, §3.1 | `measured`, nightly geometry |
| --- | ---: | ---: |
| decode call baseline | 221.4 µs (doc, `measured`) | — |
| predicted call after A | 172–193 µs | — |
| **saving A needs** | **28.4–49.4 µs** | — |
| DMA-stream saving at `bkv_p=2` (today) | — | **15.21 µs** = 6.9 % of the call |
| at `bkv_p=3` (Candidate 0) | — | 17.84 µs = 8.1 % |
| at `bkv_p=4` | — | 20.33 µs = 9.2 % |
| at `bkv_p=6` | — | **26.41 µs = 11.9 %** |
| clears the ±8.5 % instrument spread? | "yes, at both ends" | not at 2 or 3; yes at 6 |
| reaches the doc's predicted band? | — | **no, at any measured `bkv_p`** |

Two cautions on the bottom rows, in opposite directions.

**Against A: these are upper bounds on the call-level benefit, not estimates of it.** The probe
measures the DMA stream with no compute to overlap it. In the real kernel the fetch overlaps stage
A's einsum and VPU work, and any part of the stream already hidden contributes zero. P7a's finding
that stage A varies 40 % across `bkv_p ∈ {1,2,3}` at essentially constant bytes says a substantial
part is hidden.

**For A: the `bkv_p` ≥ 3 rows fetch 12 pages/sequence, not the nightly 10**, so their Δ is measured
over 768 DMAs rather than 640. Normalised to the nightly 640-DMA stream the savings are 15.21 /
14.87 / 16.95 / **22.00** µs — still short of 28.4 µs at every point, so the conclusion is unchanged,
but the raw 26.41 µs should not be read as a like-for-like nightly figure.

**A separate observation worth carrying forward, and not the question R1 was asked.** The
*incumbent's* own DMA time falls with concurrency: 74.22 → 65.32 µs at grid 16, −12.0 %, purely from
in-flight depth at an unchanged record. That is Candidate 0's effect visible in the DMA stream
alone. It is not the same as P7a's −11.91 % on the whole call and should not be conflated with it —
at `bkv_p=3`, where P7a measured its win, this probe's DMA stream improves only 2.9 %, so most of
P7a's call-level win comes from somewhere other than the fetch.

## 5. The grid-16 dispatch warning, and why the pass is still usable

The script's contamination guard fires on the grid-16 passes: the empty-launch floor is 15.69 µs
against a 38.92 µs fastest arm, 40 %. Taken at face value that would void the grid-16 absolutes.

Three reasons it does not, in increasing order of strength:

1. **The Δ column is invariant to it.** `t256 − t132` is unchanged by subtracting any additive
   per-call constant — 15.21 µs raw, 15.21 µs floor-subtracted, to the digit. §4's absolute stake
   does not depend on resolving this at all.
2. **The two grids agree.** 20.5 / 24.8 / 30.4 / 40.4 % at grid 16 against 21.0 / 25.4 / 32.0 /
   42.7 % at grid 128, across an 8× change in work per call. A fixed *additive* per-call cost cannot
   produce that; an *overlapped* one can.
3. **The floor is demonstrably host-side.** `run_dispatch_floor` builds the same `grid=(1,)` empty
   kernel regardless of `--num-grid`, and it measured 32.04, 16.75 and 15.69 µs in the three
   processes of one job — a 2× spread for identical device code. A device-side launch cost cannot
   vary 2× between processes in the same job. And `_probe_util.time_arm` enqueues `iters` calls
   behind a single `block_until_ready`, so it measures pipelined throughput, not per-call latency:
   a host cost below the device cost is hidden by construction.

**Where the warning does bite, and where this report therefore does not go:** the *floor-subtracted*
grid-16 ratio at `bkv_p=2` is 1.52 / 34.3 % saved, which would pass the gate. That reading is a
coin-flip on an unresolved modelling question, so **the gate is decided on grid 128** — whose
floor-subtracted ratio is 1.274 / 21.5 %, still failing — and grid 16 is quoted for its Δ and for
being the nightly call exactly. No verdict rests on a grid-16 ratio.

## 6. What could NOT be reproduced, and which way each cuts

Read this section before quoting the verdict.

1. **The R1 brief's "dynamically clamped length" is not what `_fetch_bkv` does.** The source clamps
   the **offset** (`safe_page_offset`) and uses a static Python extent, `sz_per_kv_packing =
   page_size_per_kv_packing` (`streamindex_topk.py:178`). It is `_fetch_bq` that clamps a length.
   The primary `indirect` arm replicates the source, not the brief. **Closed by measurement:** the
   `indirect_dynlen` arm adds the dynamic extent and moves the ratio by 0.3 %.
2. **No compute, no consumer of the fetched bytes.** `load_bkv`'s bitcast/unpack, the einsum, the
   score write-out and the SparseCore stage are all absent. This is the DMA stream in isolation.
   **Biases toward A** — it credits A with the full stream saving, which overlap can only reduce.
   §4. The one mechanism pointing the other way is HBM contention from the rest of stage A
   (`_fetch_bq`, the scores write-out), which would make bytes matter slightly more; those operands
   are small relative to K.
3. **Option A's changed *consumer* is not modelled at all.** In A the scale byte moves from
   `[..., 128:129]` of each record to a separate 8-row region, so `load_bkv` must gather it
   differently on the VPU. §3.1 asserts "the unpack does not change"; that is an assertion about a
   code path this probe never executes. **Direction: against A, magnitude unknown.** This is now the
   largest untested item in Option A's case.
4. **`bkv_p` ≥ 3 fetches 12 pages per sequence, not the nightly 10.** With `pages_per_seq = 10`,
   `num_bkv = ceil(10/bkv_p)` gives 4, 3 and 2 blocks at `bkv_p` 3, 4 and 6, hence 12 page DMAs of
   which some are clamped duplicates — the kernel's own arithmetic. The doc's P7a reports 9/10/9
   pages, implying a different nightly `kv_len`. Handled by normalising in §4; the `bkv_p = 2` row
   matches the nightly call exactly (640 DMAs, 167.77 MB).
5. **`bkv_p = 6` may not be buildable in the real kernel.** It needs a 12.58 MB VMEM double buffer
   for the incumbent record and leaves only `num_bkv = 2` blocks per grid step, which is less to
   pipeline the compute against. This probe has no compute, so it cannot see either cost. **The
   `bkv_p=6` row is evidence about the DMA engine, not a proposal.** P7 §A4 separately notes
   `bkv_p=4` is not like-for-like.
6. **The page table is synthetic** — a random permutation over 2048 pages at grid 16, random *with
   replacement* at grid 128, rather than vLLM's real and possibly clustered block-manager output.
   Affects both arms identically and the two grids agree, so it is not driving the ratio; absolute
   bandwidths could differ under a real table.
7. **The source arrays necessarily differ in footprint** (537 / 271 / 277 MB). That is Option A, not
   a confound: A halves the cache. It cannot be equalised without making one arm read padding. Any
   caching effect would favour the smaller arm, and the smaller arm is the *slower* one per byte, so
   this cannot explain the failure.
8. **Repeated measures.** Nine trials per arm are within one process and one compilation, and arms
   run in a fixed order, never A-B-A. Effective n against a systematic per-position effect is 1 per
   process. Mitigated by the effect size (21–43 % against 0.1–1.4 % spread) and by reproduction
   across two separate jobs a day apart: `j-b0e33be2` and `j-3e588eaa` give 20.93 % and 20.99 % for
   the same `indirect/bkvp2` pair at grid 128.
9. **One core of eight.** `jax.jit` ran on device 0; the pod was uncontended, so this is the clean
   case, but it is a single-core figure and should not be read as chip- or pod-level bandwidth.
10. **Correctness of Option A is not addressed here at all.** R1 is a cost question; the probe
    computes nothing and there is no consumer to be wrong. §5's separate zero-tolerance test row
    (`tests/kernels/test_dsv4_streamindex_topk.py`) still stands, unrun. **Nothing in this report is
    a correctness check.**

## 7. Two things that went wrong, recorded

**A 57-minute deadlock, `j-248bfcd5-b458-434e-b585`.** It printed the banner, the layout gates and
the dispatch floor, then hung with no arm and no error. **Cause:** the first version keyed the
double-buffer parity on the compile-time `b % 2`. With `num_bkv` odd — and nightly decode's
`num_bkv` **is** 5 — the parity flips at every grid boundary, so grid step 1 waits on semaphore 0
for a block that grid step 0 started into semaphore 1. Reproduced on the host: the schedule breaks
at global block 5, the first block of grid step 1, exactly where the log stops. The incumbent has
the same hazard and avoids it the same way this now does — by carrying the semaphore index as a
**runtime** value (`streamindex_topk.py:292-302`, `get_next_bkv_ids`) — so the fix is a fidelity
gain as well. Three guards were added: a host-side `check_schedule` simulation that replays the
exact start/wait sequence and asserts both double-buffer invariants before the TPU is touched; a
progress line before every blocking phase; and shell-level `timeout`s with `&&` chaining.
**Nothing from `j-248bfcd5` is used in this report.**

**An out-of-bounds `affine` offset.** The first version computed `safe_page_offset =
(page_indices_offset + j) * psp` with no clamp and `disable_bounds_checks=True`. At `--num-grid 128`
that reaches index 5119 against a 2048-page array — 2.5× past the end of the source. In bounds at
grid 16, which is why the two grids agreed and nothing looked wrong. **The grid-128 `affine` numbers
in `j-b0e33be2` are not quotable**; §2.2's grid-128 `affine` figures come from `j-3e588eaa`, where
the offset wraps with a `remainder`. The `indirect` and `indirect_dynlen` arms were always clamped,
so the gate's own arms were never affected, and the re-measured affine agrees with the old one to
0.5 % anyway.
