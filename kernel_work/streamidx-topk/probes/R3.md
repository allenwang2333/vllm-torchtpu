# R3 — what are stage A's 8,960 `vrot.slane`, and does Option C survive?

> ## ⚠️ STATIC COMPILE-TIME ANALYSIS, NOT A MEASUREMENT
>
> Every number in this file is an **instruction count or a scheduled-bundle count read out of
> an LLO compiler dump**. Nothing here was timed. There is no wall-clock, no throughput and no
> speedup in this document, and the two µs figures in §6 are *projections* of the design's own
> µs model onto these static counts — they are labelled "modelled" and must never be quoted as
> measured. Nothing in this file goes to `/log-experiment`.
>
> The A/B was captured by fanning three shards across one 4-chip pod. Fan-out contends for the
> host, so even if a wall-clock had been taken it would have been a ratio artefact. It was not
> taken.

**Question.** `measurement_and_design.md` §3.2 Option C ("head-major score layout", rank 2)
predicts −7.9% at prefill, and its entire magnitude comes from attributing **8,960 `vrot.slane`**
(P7b §B3.4's static histogram of `StreamIdxTC-m-bq_128-bkvp_2.1`) to the per-head reduction
`s.sum(axis=2)`. §4 Flip 2 names the failure mode: if those rotates are the **MXU drain** —
lane/sublane shuffling around `vpop.f32.mrb[*]` — then reordering the score layout removes none
of them and Option C is worth ≈0.

**Answer.** They are not the drain. **Zero** of the 8,960 rotates has a `vpop` anywhere in its
operand chain. 7,936 of 8,960 (88.6%) are removed by the head-major reorder; the residual 1,024
are fp8 matmul operand prep and store relayout, which survive any score-layout change.
**Option C's mechanism holds and it survives at rank 2** — with a correction to its arithmetic
that lands, by a different route, on almost the same number.

---

## 1. Method

Three independent lines of evidence, deliberately chosen so that no two share a failure mode.

| | what it is | what it can be fooled by |
|---|---|---|
| **A. SSA operand tracing** | walk each `vrot.slane`'s rotated operand backward and its result forward through the pure shuffles (`vcombine`/`vsel`/`vmov`) on `…-41-post-DCE-3.txt`, the last DCE before RA where every value still has a unique name | my classifier |
| **B. Rotate-immediate histogram** | count rotate amounts in `…-53-post-ra.txt`. A binary 8-sublane reduction tree uses only {1,2,4}; a single-sublane 7-way gather uses {1..7} | nothing in (A) — it is a different file and a different property |
| **C. Compile A/B** | five arms of a standalone Pallas kernel differing *only* in the reduction, LLO-dumped and histogram-diffed | a compiler that DCE'd the work away — guarded by a `vmatmul` control |

`probes/r3_shard.sh` (one arm per process — libtpu reads `LIBTPU_INIT_ARGS` once at load).

`SB=1, bq_sz=128, H=32, head_dim=128, bkv_sz=2048`, fp8_e4m3fn operands, `preferred_element_type=f32`.

The brief specified `seq_batch=2`. **The incumbent prefill dump says 1.** Its q block is

## 2. (A) SSA operand tracing — attribution of all 8,960 rotates

`…-41-post-DCE-3.txt`, incumbent prefill program. The census reproduces P7b §B3.4 exactly
(12,320 `vadd.f32` / 10,240 `vmul.f32` / 8,960 `vrot.slane` / 8,192 `vmax.f32` / 1,024 `vmatmul`),
so the reader is parsing the thing P7b quoted.

| producer of the rotated operand → consumer of the rotate | count | what it is | removed by Option C? |
|---|---:|---|---|
| `vadd` → `vadd` | **6,144** | the in-vreg 8-sublane head-reduction tree | **yes** |
| `vmul` → `vrot`(→`vsel`) | **1,792** | sublane pack: 8 broadcast reduction results gathered into one dense output vreg | **yes** |
| `vld` → `vrot`; `vrot` → `vxpose`/`vmatprep`/`vmatpush` | 256 + 128 + 64 + 64 = **512** | fp8 matmul operand prep | no |
| `vcmask\|vmand\|vmul\|vrot` → `vrot`; `vrot` → `vst` | 256 + 256 = **512** | mask → store relayout | no |
| | **8,960** | | **7,936 removable (88.6%)** |

**The direct refutation of Flip 2's drain hypothesis.** Fan-out of all 8,744
`vpop.f32.mrb[*].mxu{0,1}`:

```
    8192  vpop -> vmax        (the relu, jnp.maximum(s, 0.0))
     512  vpop -> vmul        (the weight multiply)
      16  vpop -> vunpack
      16  vpop -> vcmp
       8  vpop -> scmp
```

**Not one `vpop` reaches a `vrot.slane`.** The MXU drain on this program is `vpop → vmax → vmul`;
it never shuffles. Lead 2 (8,960 rotates ÷ 8,744 pops = 1.025) is a numerical coincidence, and a
close one — which is exactly why it needed checking rather than assuming.

### Bundle-level, from `…-71-final_bundles.txt`

Adjacency is not attribution, so the bundle view is used only to confirm the dependence the SSA
trace found, and to show why the coincidence is tempting:

```
0x292   %v42826_v57 = vrot.slane %v42825_v38, 2
0x296   %v80794_v21 = vadd.f32   %v42826_v57, %v42825_v38
```

`add(rot(x,2), x)` — a textbook tree step, the rotate feeding the add that consumes its own
un-rotated input. Rotates *do* share bundles with `vpop` (e.g. `0x27d`), but that is VLIW packing:
the two chains are disjoint in the dataflow. Address spans: tree amounts {1,2,4} across
`0x27d`–`0x2bac`; gather amounts {3,5,6,7} across `0xb50`–`0x2b84`; dynamic-amount rotates across
`0xeb`–`0x2d14`.

### Arithmetic closure, and where Lead 1 went wrong

Lead 1 predicted 6,144 rotates and 12,288 adds for the head reduction, and was written off as
"46% short of 8,960". It was right about the tree and blind to the pack:

- adds: 6,144 cross-vreg adds + 6,144 in-vreg tree adds = **12,288**, vs 12,320 measured (Δ 32) ✅
- rotates: 6,144 tree + **1,792 pack** = 7,936. The pack is the missing 29%.

## 3. (B) Rotate-immediate histogram — the independent check

From `…-53-post-ra.txt`, counting the immediate on every `vrot.slane`. This uses a different file
and a different property than §2 and agrees with it to the instruction:

| rotate amount | 1 | 2 | 4 | 3 | 5 | 6 | 7 | register (dynamic) | total |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| **incumbent** | 2,304 | 2,304 | 2,304 | 256 | 256 | 256 | 256 | 1,024 | **8,960** |
| **`head_minor` proxy** | 2,304 | 2,304 | 2,304 | 256 | 256 | 256 | 256 | 0 | **7,936** |
| **`no_reduce_x4`** | 256 | 256 | 256 | 256 | 256 | 256 | 256 | 0 | **1,792** |
| **`head_major`** | 0 | 0 | 0 | 0 | 0 | 0 | 0 | 0 | **0** |

Decompose the incumbent row:

- a 7-way single-sublane gather uses each of {1..7} once per output vreg → 7 × 256 = **1,792 pack**
- the remainder of {1,2,4} is (2,304 − 256) × 3 = **6,144 tree**
- 6,144 + 1,792 + 1,024 dynamic = 8,960 ✅

Corroborated a third way: exactly **7** distinct single-sublane `vcmask [k:k,0:127]` constants
exist (k = 1..7), and **1,792 of the 2,096 `vsel`** select on them — i.e. the pack's 1,792 rotates
and 1,792 selects are the same construct, counted twice from two directions.

## 4. (C) The compile A/B — five arms, histogram-diffed

`head_major` is Option C with q handed in already head-major (it prices Option C assuming
`load_bq` produces that ordering for free). `head_major_xpose` transposes `(bq,H,D)→(H,bq,D)`
*inside* the kernel from the incumbent's layout, and so prices that assumption. `no_reduce` and
`no_reduce_x4` are the drain controls.

### What each arm decides

**`vmatmul` = 1,024 on all five arms.** The control holds everywhere — no arm won by having its
matmul deleted.

- **`head_minor` 7,936 vs `no_reduce_x4` 1,792.** `no_reduce_x4` keeps the *entire* live MXU drain
  (8,721 pops, 8,192 of them into `vmax`, identical to `head_minor`) and the full matmul, and
  removes only the in-vreg rotate tree — **exactly 6,144 rotates disappear.** If the rotates were
  the drain, this arm would still have 7,936. Combined with the `vpop` fan-out in §2, the drain
  hypothesis is refuted twice over.
- **`no_reduce` is partially inconclusive and is reported as such.** Its `vmatmul` control holds
  (1,024), but 6,144 of its 8,337 pops went dead and `vmax` fell 8,192 → 2,048: XLA DCE'd the
  unused matmul rows' consumers even though the matmul itself stayed. This is why the
  `no_reduce_x4` arm was added, and it is `no_reduce_x4`, not `no_reduce`, that carries the drain
  verdict. `no_reduce`'s residual 1,792 rotates are the pack, which survives because the output
  store still needs it.
- **`head_major` = 0 rotates.** Option C's prediction was that the reduction becomes an aligned
  vreg add chain with no rotate at all. That is precisely what the compiler emits.
- **`head_major_xpose` = 256 rotates** plus 384 `vpack` + 384 `vcombine` + 385 `vshrl` — the
  in-kernel transpose is cheap *in the proxy*, but the proxy's q comes straight off a VMEM ref,
  so this is the optimistic end of that cost. See §7.

## 5. (C-sanity) Does the proxy reproduce the incumbent?

Required tolerance was stated up front as "within a few percent, or say so loudly".

| opcode | incumbent | `head_minor` | Δ |
|---|---:|---:|---|
| `vadd.f32` | 12,320 | 12,303 | −0.14% |
| `vmul.f32` | 10,240 | 10,240 | **exact** |
| `vmax.f32` | 8,192 | 8,192 | **exact** |
| `vmatmul` | 1,024 | 1,024 | **exact** |
| `vsel` | 2,096 | 2,048 | −2.3% |
| `vpop` | 8,744 | 8,721 | −0.26% |
| `vrot.slane` | 8,960 | 7,936 | **−1,024** |

Every opcode is within 2.3% except `vrot.slane`, which is short by exactly **1,024** — and 1,024
is exactly the *dynamic-amount* (register) rotate category, which §3's histogram shows the proxy
has zero of and the incumbent has 1,024 of, and which §2 independently classified as the
non-reduction fp8-operand-prep and store-relayout traffic. A standalone kernel reading plain VMEM
refs legitimately has no dynamically-indexed relayout. **The one place the proxy differs is the
one place the attribution predicted it would differ**, which is corroboration rather than a
defect. The proxy is sound; the verdict is not hedged on geometry.

The proxy is also 8.8% shorter in bundles (10,578 vs 11,601) and ~17% lighter in spills, both
consistent with it lacking the incumbent's pipeline and double-buffer machinery.

## 6. Verdict: Option C survives at rank 2

**The mechanism is confirmed.** The 8,960 rotates are the head reduction (6,144 tree + 1,792 pack
= 7,936, 88.6%) plus 1,024 unrelated relayout. Flip 2's first branch — "the rotates survive the
reorder" — is **closed**: `head_major` emits zero.

### Corrected arithmetic

Two corrections to §3.2's magnitude, pulling in opposite directions.

**Correction 1 — the design *understated* the op removal.** Its 89.45%-of-a-22.6%-slice figure
was derived from attributing rotates alone. Measured, `head_minor → head_major` removes:

| | `head_minor` | `head_major` | removed |
|---|---:|---:|---:|
| `vrot` + `vadd` + `vmul` + `vsel` | 32,527 | 16,655 | **15,872** |
| design's four-opcode denominator (`vadd+vmul+vrot+vmax`) | 38,671 | 24,591 | 14,080 = **36.4%** |
| all VALU-class instructions | 41,965 | 25,978 | 15,987 = **38.1%** |

Note also that P7b's denominator "39,712 VALU ops" is `vadd+vmul+vrot+vmax` **only**
(12,320+10,240+8,960+8,192), not all VALU ops — the true VALU-class count for that program is
44,594. Anyone re-deriving from §3.2 should use the right one.

**Correction 2 — a countervailing cost the design did not model.** `head_major` spills far more:
**11,266 stores / 12,832 fills** against `head_minor`'s 7,063 / 8,477, i.e. **+4,203 / +4,355**,
and 744 vs 645 spill slots. The mechanism is structural, not incidental: in head-major the 32
addends for one output vreg are 16 vregs apart in the matmul row sweep, so every partial
accumulator is live across the whole sweep; in head-minor the 4 addends are adjacent. This
counterweight is real and is the single most important thing in this report that is **not** in
the design.

**The net, and why the second job was worth running.** Op counts cannot net a −15,987 VALU
against a +8,558 spill/fill, because they issue on different slots. The scheduled bundle count
can, and it is unambiguous:

| arm | scheduled bundles | vs `head_minor` |
|---|---:|---:|
| `head_minor` | 10,578 | — |
| **`head_major`** | **8,078** | **−23.63%** |
| **`head_major_xpose`** | **8,445** | **−20.16%** |
| `no_reduce_x4` | 7,866 | −25.64% |

The extra spill traffic does **not** eat the win: the scheduler absorbs it into VST/VLD slots that
the reduction tree was not using. Option C is a ~24% shorter schedule for stage A, or ~20% if the
transpose has to happen in-kernel.

### Modelled magnitude (**modelled, not measured**)

Transferring the proxy's bundle ratio onto the design's own µs model
(stage A prefill 335.1 µs, call 857.3 µs), and assuming the reduction is proportional because
everything removed lives in the same innermost per-tile body as everything kept:

| arm | bundle ratio | Δ stage A | stage A | call | vs 857.3 |
|---|---:|---:|---:|---:|---:|
| `head_major` (q free head-major) | 0.7637 | −79.2 µs | 335.1 → 255.9 | 857.3 → 778.1 | **−9.24%** |
| `head_major_xpose` (transpose in-kernel) | 0.7984 | −67.6 µs | 335.1 → 267.5 | 857.3 → 789.7 | **−7.88%** |

**The design's −7.9% is right, reached by a route that was wrong twice in offsetting directions.**
It under-credited the removable rotates (missed the 1,792-op pack) and it ignored the spill
increase; netted at the schedule level the answer is −7.9% to −9.2% depending on where the
transpose lands. Option C **keeps rank 2**, and the range is now bounded from both sides rather
than resting on one attribution.

Decode is untouched by this probe. §3.2's "−0% to −2%" at decode stands unexamined here.

## 7. What a static dump cannot settle

Flip 2 has two branches. This report closes the second ("the rotates survive the reorder"). It
**cannot close the first**, and no static dump can:

1. **Static mix ≠ dynamic mix.** Every count above is instructions the compiler *emitted*, not
   instructions the machine *executed*. If the reduction tree sits in a region with a lower trip
   count than the rest of stage A, its share of real cycles is smaller than its share of the
   schedule and the −7.9%/−9.2% shrinks. The bundle count in §6 is a better proxy than an opcode
   count because it accounts for scheduling, but it is still code length, not a cycle count. Only
   a hardware capture settles this — and the one route to real per-cycle counters on v7x
   (`/xprof-llo`'s periodic GFC sampling) is documented as verified on exactly one selftest matmul
   and never on a kernel like this, with a 16-bit counter that wraps at ~34 µs.
2. **`load_bq` is priced by assumption, at both ends.** `head_major` assumes q arrives head-major
   for free; `head_major_xpose` prices an in-kernel transpose from a VMEM ref, which is the
   *optimistic* version of the alternative, because the real Option C would change `load_bq`'s
   DMA/layout and this probe sees none of that. The true cost of getting q head-major is outside
   the four corners of this dump.
3. **Numerical equivalence was not checked.** These arms were compiled and run once for the dump;
   no output was compared against the incumbent. `head_major` is not even given the same input
   layout. This is a compile-structure probe, not a correctness check, and Option C still needs
   its own.
4. **Spill behaviour is proxy-specific.** The +4,203/+4,355 spill delta was measured on a
   standalone kernel with 645 spill slots against the incumbent's 1,375. The incumbent is under
   substantially more register pressure already, so the head-major live-range extension could be
   worse there than here. §6's bundle net is measured on the proxy, not the incumbent.
