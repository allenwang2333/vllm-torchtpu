## Constraint sheet — Area (7): what is computed once, and where it is kept

**Block:** `streamindex_topk` scoring half, GLM-5.2 DSA lightning indexer. Source tags below are `[source: <path>@ab80889f:<lines>]`, working tree clean for all three files read.

### 0. One premise of the brief is wrong, and it rescales every count in §4

The brief says "78 layers, so anything rebuilt per layer is rebuilt 78 times per step." It is **21**, not 78. GLM-5.2's checkpoint sets `index_topk_freq = 4`, `index_skip_topk_offset = 3`, `index_topk_pattern = null` `[source: gs://tpu-commons-ci/glm/GLM-5.2-FP8/config.json]`, and vLLM computes `_skip_topk = max(layer_id - offset + 1, 0) % freq != 0` `[source: vllm/model_executor/models/deepseek_v2.py:1104-1106]`, which `GlmMoeDsaForCausalLM` inherits `[source: vllm/model_executor/models/deepseek_v2.py:1936]`. Evaluated: layers `{0,1,2,6,10,…,74}` — **21 of 78**. The checkpoint's own `indexer_types` list independently agrees (21 `"full"`, 57 `"shared"`, at exactly those indices). The other 57 layers reuse `topk_indices_buffer` `[source: mla_attention_op.py@ab80889f:605-607]`. **Every "rebuilds per step" in §4 is 21×, not 78×** — a factor 3.7 on the whole area's prize. `measured` origin: none; this is `[source: …]` arithmetic over a config file, not a probe.

### 1. What this area forbids or requires at step 1's shapes

- **Requires: the level-3 CSE assumption be dropped for this block.** Each indexer layer builds its own torch custom op with a per-layer name, `op_name = f"pallas::streamidx_topk_{prefix}"` `[source: mla_attention_op.py@ab80889f:125]`, dispatched through `tpu_torch_pallas.call_custom_kernel` as a self-contained exported StableHLO module `[source: torch_tpu/_internal/pallas/pallas.py:514-517, 684-690]`, and `streamindex_topk` is itself `@jax.jit` `[source: streamindex_topk.py@ab80889f:509-520]`. There is no single XLA graph spanning the 21 layers, so **nothing in `_common_path` can be CSE'd across layers**. The reference file's level-3 rung — "once per layer, or once per step if CSE holds" — resolves to *once per layer* here, unconditionally.
- **Forbids nothing on SMEM grounds.** Total SMEM operand footprint is `2,848 B` at the production geometry (`max_num_seqs=64`, `pages_per_seq=9`) against a `1,048,576 B` ceiling — 0.27%. Even at a 64k-advertised config it is `17,184 B`, 1.6%. `modelled` from the shapes at `[source: streamindex_topk.py@ab80889f:695-701]`.
- **Requires the `max_model_len`→padded-width chain be treated as a metadata decision, not a shape accident.** `num_sublanes_total` is a level-1 Python int derived from `max_model_len`, and it sets `slice_len` inside the SparseCore, which is DMA'd in full per row regardless of `row_lengths` (§2, last bullet).

### 2. Tagged facts from `07-precomputation.md` that bear on this block

- **SMEM ceiling: 1,048,576 bytes per core, not divided by anything; a scratch bisect reached 261,504 int32 scalars = 1021.5 KiB, headroom ~4 KiB** `[verified: j-ed517191-5f2d-4d00-8c0c, smem_scratch_bisect]`. This block uses 0.27% of it.
- **Level 3 vs level 4 is worth nothing on speed at ~1024 entries** — 0.96x and 1.07x in two jobs, disagreeing on direction `[verified: j-a35c902f-5066-43e2-90a3, precompute_outside_versus_inside]` `[verified: j-85d7b244-e1df-4e9d-b3a4, precompute_outside_versus_inside]`. Every metadata array here is ≤ 4,160 entries, so this block sits entirely inside the region where the choice is free.
- **In-kernel SMEM scalar fill: 6.92 ns/scalar slope (6.85 ns in a second job), N=1024 inside the noise of an empty kernel** `[verified: j-a35c902f-5066-43e2-90a3, smem_scalar_fill_cost]` `[verified: j-85d7b244-e1df-4e9d-b3a4, smem_scalar_fill_cost]`. Nothing here approaches the "tens of thousands" threshold.
- **A scratch written at grid step 0 is still there at step 7** `[verified: j-85d7b244-e1df-4e9d-b3a4, scratch_persists_across_grid_steps]` — the precondition any level-4 hoist in this kernel would stand on.
- **A prefetched scalar array does drive `index_map`s** `[verified: j-85d7b244-e1df-4e9d-b3a4, scalar_prefetch_drives_index_map]`. This kernel already uses `PrefetchScalarGridSpec(num_scalar_prefetch=6)` `[source: streamindex_topk.py@ab80889f:713-714]` but has no `index_map`s at all — every `in_spec` is whole-array `pltpu.HBM` `[source: :645-652]` and all fetching is hand-rolled DMA. The mechanism's highest-value spend is unused here by construction.
- **Mosaic hoists the grid-invariant *producer*, not the *reduction/comparison* over it; a VMEM-hoisted table recovered only 13% of the gap (223.8 µs vs 230.3 µs recompute vs 180.1 µs smem_hoist)** `[verified: j-a35c902f-5066-43e2-90a3, grid_invariant_recompute_cost]`. Bears directly on `k_span` / `valid_mask` / `bq_pos_compressed_vec`: the `jnp.arange` producers will fold, the comparisons that consume them will not.
- **Dynamic grid: 26.2 µs fixed + 0.427 µs per grid step; 1.81x at grid 8-vs-64 against an ideal 8x; at grid=8 the fixed term is 88% of the call** `[verified: j-0a0a72c8-37fe-4929-a6e0, dynamic_grid_from_smem_skips_work]`. This kernel has a data-dependent grid `[source: streamindex_topk.py@ab80889f:643]` and allocates its output at the padded maximum `[source: :725-728]`, which is exactly the configuration the file says it did not isolate.
- **All six of int32/int16/int8/uint32/bool/float32 work in SMEM as scratch and as operand** `[verified: j-85d7b244-e1df-4e9d-b3a4, smem_metadata_dtype_support]`. Available, and not needed at 0.27% occupancy.
- **`[source: …@9da2369]` idioms available and unused here:** `jax.tree.map(lambda _: smem_spec, metadata_obj)` for a one-line metadata tree (GDN wrapper 419-420, 455-475); `pl.ds(row_start, row_size)` with both args traced in an `index_map` (gmm_v2 305-338); dynamic `emit_pipeline` grid read from SMEM (GDN wrapper 218-225).

**One source-level finding that answers step 1's open probe #6.** `_sc_topk_direct`'s per-row read is `dma(scores_hbm.at[pl.ds(s, slice_len)], resident_vmem, 1)` with `slice_len` **static** `[source: sparsecore_topk.py@ab80889f:155-160, 324]`; only the *scan* bounds (`i_hi`, `walk_chunks`, `valid = j < i_hi`) follow `row_lengths`. So the SparseCore's HBM read is **O(padded width)**, not O(`row_lengths`), and `num_sublanes_total` — a level-1 quantity keyed on `max_model_len` — sets it. This is read from source, not measured; it predicts, and does not establish, that a long-context config taxes every short request. The corollary for #3: the `-inf` *values* beyond each row's `row_length` are read into VMEM but never consumed, and columns below `row_length` are always inside the kernel's own written region (`row_length ≤ kv_len ≤ num_bkv × bkv_sz`), so **`scores_init`'s values appear to have no consumer at all** — a claim that stands or falls on that reading and belongs in a probe, not in a design.

### 5. Alternatives this area could take — enumerated, none chosen

**On `scores_init` (#3):**
- **A1** Leave at level 3 as-is. Costs `modelled` 82.3 µs × 21 per step at `mixed_64k`; zero risk.
- **A2** Narrow the fill to the unwritten sublane tail only, extent `num_sublanes_total − num_bkv×num_sublanes_bkv`, computed at level 3 from `max(seq_lens)`. Recovers 80–97% of #3 (§4 row 3a). **Staleness risk: none across batch shapes** — the extent is recomputed per call — but it *does* couple the fill to the kernel's own `num_bkv` arithmetic in two places, and a `bkv_p` change that updates one and not the other under-fills silently on the long-KV shape only.
- **A3** Drop the fill entirely, on the reading above that its values have no consumer. **The alternative with a correctness cliff**: it is right only if `sparsecore_topk`'s scan bound never exceeds the kernel's written width for any row, on every band including the DECODE-remainder band at `distribution[0] % 4 ≠ 0` and the padding rows where `eff_row_lengths` returns 0. Reproduces as garbage indices on a batch shape not tested, which is precisely the failure mode `AREAS.md` names.
- **A4** Hoist the `-inf` buffer to level 2 (allocate once at model load). **Buys nothing**: it is `input_output_aliases`'d to the output `[source: :729]` and destroyed by the kernel, so it needs re-filling every call regardless. Recorded because "allocate once" reads like a win and is not.
- **A5** Move the fill inside the kernel as a level-4/5 write of the tail sublanes, using the DMA machinery already at `:137-151`. Trades XLA HBM traffic for kernel HBM traffic at the same byte count unless combined with A2; its real content is removing a separate XLA-level pass, which is area (1)'s ledger, not mine.
- **A6** Shrink `num_sublanes_total` (#1) from `max_model_len` to a per-step bucketed KV length. Cuts #3, #19's VMEM scratch, and the SparseCore's O(padded width) DMA together. **This is the staleness trap of the set**: `num_sublanes_total` is level 1 and feeds an output *shape*, so making it batch-dependent means recompiling per bucket — and a bucket boundary that is wrong for one batch shape produces a too-narrow scores buffer, not a slow one.

**On the step-invariant XLA metadata (#4, #5, #8, #9, #10):**
- **B1** Leave at level 3, 21× per step. The status quo; each item is individually small and `unmodelled`, and their sum is exactly the cost the file warns is invisible to a kernel profile.
- **B2** Hoist to a per-step level in the runner: compute `eff_row_lengths`, the scatter indices, `decode_batch_end` and `distribution` once and pass them as operands to all 21 indexer layers. This is the cross-repo move the file calls "the level most often missed" — the code that would do it is in the model runner, not the kernel. **Staleness risk: high and shape-specific**, because the hoisted values would have to be invalidated on every scheduler decision; getting that wrong is silently-wrong indices, not a crash.
- **B3** Hoist only inside one layer's op — merge the three `pallas_call` bands' shared scalars (#6, #7) so they are built once per call rather than 3×. Removes 42 of 63 tiny builds; `unmodelled` benefit.
- **B4** Move `eff_row_lengths` to level 4 (an in-kernel SMEM scratch fill). At ≤4,096 entries the two levels measured 0.96x and 1.07x `[verified: precompute_outside_versus_inside]`, so this is a legibility/plumbing choice and not a speed one — and it does not help, because the 21× repetition is the cost, not the level.
- **B5** Lift the `lax.cond` predicate (#10) to the runner as a Python bool and select the branch at trace time. Removes a whole-batch device reduction and the branch machinery. **Staleness: this is the shape-dependent hoist par excellence** — a trace-time decision that `max(seq_lens) ≤ k` is wrong the first time a long request joins the batch, and the failure is wrong output, not a recompile.
- **B6** Delete `topk_indices_buffer[:ntok] = -1` (#11) given the immediately-following full overwrite. `modelled` 52.4 µs/step at mixed. **Correct only while `num_out == hidden_states.shape[0]` and `topk_tokens == buffer.shape[1]`**, both of which hold at this config and neither of which is asserted in code. This is a caller-side edit, not a kernel edit — a `carried:` item.

**On the in-kernel level-5 quantities (#12, #14, #16):**
- **C1** Leave as-is; each is `unmodelled` and the file's own measurement says a VMEM hoist of a grid-invariant table recovers only 13% of the available gap.
- **C2** Make `num_bq` (#14) a Python int on the `static_q_len is not None` path, giving `lax.fori_loop` a static trip count. Costs one branch in the wrapper; no staleness (both inputs are already static). The MIXED path must stay dynamic.
- **C3** Swap the loop nest so `bkv` is outer and `bq` inner, making `valid_mask` (#16) naturally invariant across the inner loop. **This is not mine to take** — it changes which operand is re-read from HBM `num_bq` times, which is step 1's `hbm_st` term and belongs to area (2)'s traversal order. Named here so pass 2 can see the seam.
- **C4** Hoist `valid_mask` into a VMEM or SMEM scratch at level 4, indexed by `bkv_idx`. SMEM has 1 MiB free and bool is a supported SMEM dtype `[verified: smem_metadata_dtype_support]`; VMEM competes with area (2)'s block sizes. The applicable recompute estimate is the file's ~540 ns/step figure, not its 98 ns/step measurement, because this mask is operand-seeded rather than iota-seeded — see the third `## Gaps` row.
- **C5** Precompute a per-sequence `num_bkv` table at level 3 into SMEM and read it per grid step, in place of the `jnp.max(jnp.stack(kv_lens))` at `:275`. ~64 entries; free by the 6.9 ns/scalar slope. Enables the sorted-sequence TODO at `:751-754` — but **the sort permutation's *effect* (less ragged waste) is area (2)**; only *where the permutation is computed* is mine, and the answer there is level 3, once per step, ~64 int32 in SMEM.

**Scope boundaries I am not claiming:** whether the `-inf` fill is replaceable by in-kernel tail masking is area (4)'s padding-vs-masking call as much as mine; whether the 256-byte cache record is narrowed is area (1)/(4); the loop-order swap in C3 is area (2); the sort in C5 is area (2). The `slice_len` finding is about the selection half, which step 1 placed outside the block — it is reported because `num_sublanes_total`, the quantity that sets it, is mine.
