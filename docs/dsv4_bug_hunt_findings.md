# DSV4 Bug-Hunt Findings

**Date:** 2026-07-28. Produced by running the audit in `docs/dsv4_bug_hunt_prompt.md`
against the current state of `patemotter/dsv4-correctness-fixes`. Companion to
`docs/dsv4_architecture_and_rationale.md` (the correctness investigation) and
`docs/dsv4_pr_splitting_plan.md` (the PR-splitting workstream).

**Method:** direct diff against `~/workspace/tpu-inference` (the trusted reference) for
every DSV4 file with a same-named counterpart; static trace + a dedicated research pass
for `cache_config.block_size`'s real runtime value; and — critically — mining the
existing `scratch/*.log` files from real full-model runs (this repo already has
extensive, previously-armed debug instrumentation) for hard runtime evidence rather than
relying on static reasoning alone wherever possible. Real config used throughout:
checkpoint `config.json` (`compress_ratios` per-layer, `sliding_window=128`,
`head_dim=512`, `index_n_heads=64`, `num_attention_heads=64`), and
`cache_config.block_size` values empirically observed as **16** (default
`run_dsv4_inference.py`, `max_model_len=64`) and **32** (session 8's long-prompt test,
`max_model_len=512`) — both confirmed two independent ways (a from-source static trace,
and grepping real `[DEBUG_SWA]`/`tpu_runner.py:805` log lines from actual runs).

## Finding 1 (highest priority, UPDATED after fresh runtime verification — see
correction note below): HCA's `compress_ratio` is silently clamped in the registered
KV-cache-spec; the clamp is real and reachable at every `max_model_len` tested so far,
but its worst-case consequence does not survive contact with a fresh run of the current
code

**Correction note, read this first:** an earlier draft of this finding used arithmetic on
*old* `scratch/*.log` output to argue the clamp has no real consequence at all (two
layers with different `compress_ratio` showed the same `page_size=81920` in an old log).
That was the wrong way to check this — it wasn't confirmed that log was even generated by
the current code, and the reasoning was reverse-engineered from two numbers rather than
from the actual formula. Correctly called out and redone: read
`MLAAttentionSpec.real_page_size_bytes` directly from `vllm/v1/kv_cache_interface.py:369-384`
(confirms it *does* route through the clamped value, contradicting the old-log
reasoning), then added fresh `[DEBUG_SPEC_SIZING]` instrumentation directly in
`get_kv_cache_spec()` and re-ran the model from scratch. The verified result is below —
it's more nuanced than either the original hypothesis or the mistaken refutation.

**Files:** `src/vllm_torchtpu/layers/vllm/custom_ops/deepseek_v4.py:1047-1057`
(`VllmDeepseekV4MLAAttention.get_kv_cache_spec`) and `:793-804`
(`VllmDeepseekV4IndexerCache.get_kv_cache_spec`).

```python
def get_kv_cache_spec(self, vllm_config: VllmConfig) -> KVCacheSpec | None:
    block_size = vllm_config.cache_config.block_size
    comp_ratio = max(1, self.compress_ratio)
    return MLAAttentionSpec(
        block_size=block_size,
        ...
        compress_ratio=min(comp_ratio, block_size),   # <-- clamp
        alignment=None,
    )
```

**The reference does not clamp this at all.** `tpu-inference`'s
`deepseek_v4_attention.py:161-176`:
```python
def get_kv_cache_spec(self, vllm_config: VllmConfig) -> KVCacheSpec | None:
    if (self.compress_ratio <= 1):
        return None
    return MLAAttentionSpec(
        block_size=vllm_config.cache_config.block_size,
        ...
        compress_ratio=self.compress_ratio,   # <-- real value, unclamped
        alignment=None,
    )
```

**What it evaluates to under the real config.** `self.compress_ratio` for a real HCA
layer is **128** (confirmed via this repo's own `[DEBUG_SWA]` runtime print — see
Finding 3 below for the log evidence of this print firing per-layer). `cache_config.block_size`
resolves to **16** for the default `run_dsv4_inference.py` invocation
(`max_model_len=64`, traced through `tpu_platform.py:700-731` →
`PallasAttentionBackend.get_page_size()`, `layers/vllm/attention.py:392-406`:
`next_power_of_2(64)//16 = 4`, clamped up to the function's own 16-minimum) and **32**
for session 8's `max_model_len=512` run (`next_power_of_2(512)//16 = 32`). Both are
independently confirmed empirically: `scratch/dsv4_fullrun_longprompt_session8.log`
literally prints `model.layers.3.attn: MLAAttentionSpec window=None compress=32
page_size=81920` for layer 3 — **the first HCA layer, whose real `compress_ratio` is
128, has `compress=32` on its own registered cache spec.** That is
`min(max(1,128), 32) = 32` firing exactly as read from the source, not inferred.

This clamped value feeds vLLM's own `MLAAttentionSpec.storage_block_size` property
(`vllm/v1/kv_cache_interface.py:366-367`): `return self.block_size // self.compress_ratio`.
Since the clamp forces `compress_ratio` to equal `block_size` whenever the real ratio
(128) exceeds it (true for every `block_size` below 128, i.e. every `max_model_len`
below **2048**), `storage_block_size` self-divides to exactly **1**. `MLAAttentionSpec`
(read directly from `vllm/v1/kv_cache_interface.py:369-384`, not inferred) overrides
`real_page_size_bytes` specifically to use `storage_block_size` instead of the base
class's plain `block_size` — confirming the degenerate value does flow into the page-size
computation at the *source*, not just in theory.

**Fresh verification (this session, after the correction above):** added
`[DEBUG_SPEC_SIZING]` prints directly inside both `get_kv_cache_spec()` methods
(`custom_ops/deepseek_v4.py`), capturing `storage_block_size`/`real_page_size_bytes`/
`page_size_bytes`/`page_size_padded` at the moment the spec is constructed, then ran the
model fresh end-to-end (`scratch/dsv4_verify_spec_sizing.log`, default config,
`max_model_len=64` → `block_size=16`). Confirmed at the source, current code, this run:

```
model.layers.3.attn (main attn, HCA): real_compress_ratio=128 block_size=16
    spec.compress_ratio=16 storage_block_size=1 real_page_size_bytes=640
    page_size_bytes=640 page_size_padded=None
model.layers.2.attn (main attn, CSA): real_compress_ratio=4 block_size=16
    spec.compress_ratio=4 storage_block_size=4 real_page_size_bytes=2560 [not clamped]
model.layers.0.attn (main attn, dense): real_compress_ratio=1 block_size=16
    spec.compress_ratio=1 storage_block_size=16 real_page_size_bytes=10240 [not clamped]
```

This confirms the degenerate 640-byte/1-row-per-page value genuinely is what
`get_kv_cache_spec()` declares for HCA layers at construction time — the clamp and its
formula are real, exactly as predicted.

**But the actual allocated tensor is NOT sized to this degenerate value.** The existing
`[DEBUG_FORWARD_MQA_CACHES]` print (already armed in this file) captured the *real* bound
tensor for the same layer in the same run:
```
model.layers.3.attn: main_cache_kv.shape=torch.Size([2522, 16, 1, 4, 640])
```
i.e. (after squeezing the middle `1` dim) `[num_pages=2522, 16, 4, 640]` — a real per-page
capacity of `16*4=64` rows (`k_block_size = cache.shape[1]*cache.shape[2]`, the same
expression the compressor's own addressing code uses), **64× larger than the degenerate
640-byte/1-row computation**, and `page_size_padded` was still `None` at the moment the
spec was constructed — meaning something in vLLM's later group-merge/unify step (which
runs after collecting every layer's spec, out of scope for this session's trace) grows
the real allocation well past what the clamped `storage_block_size=1` alone would give.
The compressor's own read/write addressing (`k_cache_block_num`/`k_cache_block_offset` in
`custom_ops/deepseek_v4.py`) re-derives its row-capacity directly from this real bound
tensor's shape, not from the spec's declared `compress_ratio`/`storage_block_size` — so it
stays self-consistent with whatever the real allocation turns out to be.

**Net effect of the fresh verification:** the clamp is real, confirmed at the source, and
still a genuine, uncommented divergence from the reference (which never clamps this
value at all) — but the specific catastrophic consequence originally hypothesized (a
physical page sized for exactly one compressed row) is refuted by directly observing the
current code's real allocation. What replaces it is a narrower, still-open question: the
real per-page capacity (64 rows × `compress_ratio=128` = **8,192 real token positions per
physical page**) is a value that doesn't obviously trace back to any deliberate design
target I've confirmed (not the reference's own numbers, not a value stated anywhere in
this codebase's comments) — it's an *emergent* result of the clamp plus whatever
downstream correction grows it, and I have not verified it's the *right* emergent
result, only that it isn't the *most degenerate possible* one. Concretely: no run in this
entire investigation (this fresh one included) has ever pushed a sequence past ~600
tokens — nowhere near the 8,192-token point where a second physical page would first be
needed for an HCA layer's compressed cache. **Whatever happens at that boundary (correct
continuation, corruption, or a crash) is completely untested**, and is now the
single most precisely-scoped open question from this pass: it would take a real run of
several thousand tokens to find out, which is a materially bigger ask than the
verification done this session.

## Finding 2: three separate silent-fallback-to-a-wrong-layer's-metadata sites
(pattern 5), confirmed absent in the reference

**File:** `src/vllm_torchtpu/layers/vllm/custom_ops/deepseek_v4.py`, three sites:

1. `VllmDeepseekCompressor.forward`, lines 644-654:
   ```python
   prefix_key = getattr(getattr(self, "state_cache", None), "prefix", None)
   state_metadata = attn_ctx.get(prefix_key, next(iter(attn_ctx.values()), None))
   ...
   k_cache_metadata = attn_ctx.get(k_cache_prefix_key, state_metadata)
   ```
2. `VllmDeepseekV4Indexer.forward`, lines 895-898:
   ```python
   prefix_key = getattr(getattr(self, "k_cache", None), "prefix", None)
   attn_metadata = attn_ctx.get(prefix_key, next(iter(attn_ctx.values()), None))
   ```
3. `forward_mqa`, lines 1287-1292:
   ```python
   swa_attn_metadata = attn_ctx.get(swa_layer_name, attn_ctx.get(main_prefix, next(iter(attn_ctx.values()), None)))
   ...
   main_attn_metadata = attn_ctx.get(compressor_state_prefix) or attn_ctx.get(main_layer_name) or swa_attn_metadata
   ```

`docs/dsv4_architecture_and_rationale.md` §4 already flagged **one** instance of this
("the compressor's `attn_ctx.get(prefix, next(iter(...)))` silent-fallback... a latent
silent-wrong-answer risk if a prefix ever fails to match") but described it as unchanged
and didn't trace how many places it actually appears, or compare against the reference.

**Direct comparison against `tpu-inference` confirms this is a vllm-torchtpu-specific
pattern, not shared design.** The exact same three lookups in the reference all use
plain dict subscripting, which raises a loud `KeyError` on any miss instead of silently
substituting another layer's data:
- `deepseek_v4_compressor.py:128-129`: `state_metadata = attn_metadata[self.state_cache.prefix]`
  / `k_cache_metadata = attn_metadata[self.k_cache_prefix]`
- `deepseek_v4_indexer.py:162`: `attn_metadata = attn_metadata_dict[self.k_cache.prefix]`
- `deepseek_v4_attention.py:315,335`: `swa_attn_metadata = attn_metadata[swa_layer_name]`
  / `main_attn_metadata = attn_metadata[main_layer_name]`

**Reachability:** `next(iter(attn_ctx.values()), None))` only actually *fires* when the
primary key lookup misses. §3.8 of the architecture doc already confirmed, via live
diagnostic print, that `attn_ctx[compressor_state_prefix] is attn_ctx[main_layer_name]`
for both a CSA and an HCA layer in at least one concrete run — i.e. the primary lookups
*are* succeeding in the cases checked so far. I did not find a config/scenario in this
pass where the fallback demonstrably fires (no `[DEBUG_...]` print exists on this
exact path to check log evidence the way Finding 1 could be checked). **Likely
explanation for why this defensive code exists at all:** `self.k_cache`'s effective
`.prefix` is not a simple, statically-guaranteed attribute the way the reference's
`self.k_cache_prefix` is — it depends on the `self.mla_attn = self` aliasing collapse
(`dsv4_architecture_and_rationale.md` §1.2/§2.4) that has no equivalent in the
reference's unaliased class structure, which is plausibly *why* vllm-torchtpu grew these
fallbacks in the first place (uncertainty about whether `.prefix`/`.custom_prefix`
always resolves correctly post-aliasing), not arbitrary defensiveness.

**Recommended fix:** replace all three with the reference's direct-index behavior (or at
minimum, `raise` with a clear message on miss instead of silently substituting), matching
the "never guess" precedent already established elsewhere in this exact file
(`_build_attn_op`'s `swa_cache_layer.block_size` `RuntimeError` guard, `:1070-1077`).
Currently unreachable-by-known-evidence, but exactly the shape of bug that stays invisible
until a scheduling/prefix-caching edge case exercises it — worth closing before relying on
any config beyond what's been manually spot-checked.

## Finding 3: `get_kv_cache_spec` allocates a spurious main-attention cache-spec for
SWA-only/dense layers — confirmed via real runtime logs, currently inert for
correctness but wastes HBM

**File:** `src/vllm_torchtpu/layers/vllm/custom_ops/deepseek_v4.py:1047-1057` (same method
as Finding 1). Missing the reference's `if self.compress_ratio <= 1: return None`
early-return (`deepseek_v4_attention.py:161-164`) — vllm-torchtpu's version always builds
and returns a real `MLAAttentionSpec`, for every layer including the two dense/SWA-only
ones.

**Confirmed via real runtime evidence, not just code reading.**
`scratch/dsv4_fullrun_longprompt_session8.log`:
```
model.layers.0.attn.swa_cache: SlidingWindowMLASpec window=128 compress=1 page_size=20480
model.layers.0.attn: MLAAttentionSpec window=None compress=1 page_size=81920
```
Layer 0 (`compress_ratio` clamped by vLLM's own base class to `max(1, 0) = 1` — see the
"checked and refuted" section, this is *not* a literal 0) gets **both** its legitimate
`.swa_cache` spec *and* a spurious plain `.attn` `MLAAttentionSpec` that the reference
would never register for this layer at all (it returns `None` and vLLM's spec-collector
skips it). Confirmed present in every log checked (`native_venv_full_run2.log`,
`full_run_after_optionA.log`, `dsv4_fullrun_longprompt_session8.log` — including both the
default-`max_len=64` and the `max_len=512` runs).

**Traced consequence:** `forward_mqa` computes `main_attn_metadata` for this spurious
key unconditionally, but only *reads* its fields inside `if not swa_only and
main_attn_metadata is not None:` (`:1316`) — for `swa_only=True` layers this branch is
never entered, so the spurious metadata is fetched and discarded, never feeding into the
actual attention computation. **Currently reachable but not proven to cause wrong
output** — the confirmed cost is an unnecessary extra KV-cache-spec-group allocation (real
HBM, `page_size=81920` bytes/page × however many pages get allocated for it) for exactly
2 of 43 layers, plus one dead dict lookup per forward call. Worth fixing to match the
reference and stop wasting HBM, especially since Finding 1 shows HBM/page-size headroom
in this exact area is already fragile.

## Finding 4: hardcoded `128`-alignment replacing dtype-packing-derived alignment in
the indexer's top-k kernel (pattern 2) — investigated, likely benign but undocumented

**File:** `src/vllm_torchtpu/kernels/deepseek_v4/streamindex_topk.py:497,517`
(`prepare_q_inputs`, `prepare_index_weights`).

```python
q_packing = get_dtype_packing(q.dtype)      # computed...
num_q_heads = align_to(actual_num_q_heads, 128)   # ...but not used here anymore
```

Reference (`tpu-inference`'s same file, same functions): `align_to(actual_num_q_heads,
get_dtype_packing(q.dtype))`. Not mentioned anywhere in
`dsv4_architecture_and_rationale.md`'s otherwise-exhaustive per-file diff notes.

**What it evaluates to under the real config:** `get_dtype_packing(dtype) = 32 //
get_dtype_bitwidth(dtype)`. For the fp8 query tensor used here, that's `32 // 8 = 4`.
Real `actual_num_q_heads` for this checkpoint (TP=1 effective, per
`dsv4_architecture_and_rationale.md`'s EP/TP analysis) is **64**
(`index_n_heads`/`num_attention_heads` both 64). Reference:
`align_to(64, 4) = 64` (no padding at all). vllm-torchtpu: `align_to(64, 128) = 128` — a
full 2x pad, not the reference's zero-pad.

**Investigated for correctness, not just flagged:** both `prepare_q_inputs` (`q`) and
`prepare_index_weights` (`index_weights`) zero-pad the added rows
(`constant_values=0` at both call sites, `:506` and `:524`). The lightning-indexer score
is a linear weighted sum across heads (`weights[h] * dot(q[h], k)`), and with both
operands zero on the padding rows, their contribution is exactly zero regardless of `k`.
Downstream reads slice back to `[:actual_num_q_heads]` before anything that looks like a
final reduction (`:350-355`). **This is very likely benign** — but I did not fully trace
every intermediate step of the ~200-line Pallas kernel body between the padding and the
final slice to rule out a non-linear per-head operation (e.g. any per-head max/softmax)
being applied to the padded buffer before the slice, which would not be zero-safe.
Real, confirmed cost regardless of correctness: doubles this kernel stage's compute/VMEM
footprint (64→128 heads) for no evident reason tied to this checkpoint's actual shapes.
**Recommend:** either restore the packing-derived alignment (matching the reference) or
add a one-line comment explaining why 128 is deliberately used instead, so a future
reader doesn't have to re-derive this.

## Checked and refuted (valuable negative results — do not re-open these)

**Divide-by-zero for `compress_ratio=0` layers.** `forward_mqa`'s
`extra = (positions + 1).to(torch.int32) // self.compress_ratio` (and the reference's
identical line, `deepseek_v4_attention.py:330`) looked like a live risk for layers 0/1,
whose checkpoint config value is literally `0`
(`compress_ratios[0]=0, compress_ratios[1]=0`, confirmed via direct `config.json`
parsing). **Refuted empirically**: `scratch/dsv4_fullrun_longprompt_session8.log`'s
`[DEBUG_SWA]` prints show `Layer model.layers.0.attn compress_ratio=1` (not 0) —
confirming vLLM's own base class (`vllm/models/deepseek_v4/attention.py:179`:
`self.compress_ratio = max(1, config.compress_ratios[layer_id])`, per the background
trace for Finding 1) clamps this to a minimum of 1 before either repo's code ever reads
`self.compress_ratio`. Both repos share this assumption safely. Not a bug.

**SWA cache's hardcoded `csa_compression_ratio = 4` divisor.**
`VllmDeepseekV4SWACache.__init__`'s `self.block_size = min(cache_config.block_size // 4,
window_size)` looked like a Pattern-2 "wrong constant borrowed out of context" candidate
(hardcoding CSA's ratio for a cache used by dense/SWA-only layers too). **Refuted by
direct comparison**: `tpu-inference`'s identical class has the exact same hardcoded `4`
and the exact same comment ("We would like to overlay the SWA cache with CSA's main
cache on the same KV-Tensor. Thus set swa cache's block size accordingly.") — this is the
SWA cache's own fixed physical-packing convention, deliberately independent of the owning
layer's actual compression ratio, not a copy-paste error. Not a bug.

**`VllmCompressorStateCache.get_kv_cache_spec`'s `rows_per_token = page_size //
self.block_size`.** A second chained-division site feeding cache geometry
(`:550-552`). Checked against the real, empirically-confirmed `cache_config.block_size`
values: at block_size=16, `16 // 4(CSA) = 4` and `16 // 8(HCA) = 2`; at block_size=32,
`32 // 4 = 8` and `32 // 8 = 4` — clean divisions, no silent truncation at either
observed config. **Currently safe, but fragile and unasserted**: this would silently
truncate for any `cache_config.block_size` not an exact multiple of 4/8, which the
`get_page_size()` curve does not guarantee in general (it does for the values checked
here). Low priority; worth an assertion if this is ever touched.

**`bl_double_buf`/`bm_double_buf` and `l_scratch`/`m_scratch` aliasing in
`mla.py`/`mla_swa.py`.** The reference aliases these pairs (`bm_double_buf =
bl_double_buf`, `m_scratch = l_scratch` — literally the same VMEM scratch object for
what are semantically the running-max and running-sum of an online-softmax) in **both**
kernel files. vllm-torchtpu gives each an independent `pltpu.VMEM(...)` allocation in
both files instead. This is a real, systematic (applies identically to both files)
divergence, present in neither `dsv4_architecture_and_rationale.md`'s per-file diff notes
nor anywhere else in the investigation's documentation. **Not a live bug in
vllm-torchtpu** — its version is the safer one (no buffer sharing between what should be
independent state) — but undocumented, and worth a one-line comment at both sites
explaining that the separation is intentional, so a future "resync with upstream" pass
doesn't silently re-introduce the aliasing while trying to reduce a diff.

**Checkpoint config oddity (not a vllm-torchtpu bug):** the real checkpoint's
`config.json` has `len(compress_ratios) == 44` for `num_hidden_layers == 43` — one extra,
unused list entry (index 43, value 0). Confirmed harmless: layer construction only ever
indexes 0-42, and the runtime `[DEBUG_SWA]` compress_ratio values observed for every
layer 0-42 match straightforward `compress_ratios[layer_id]` indexing with no shift.
Worth knowing about if this checkpoint's config is ever regenerated or compared byte-for-byte
against another source, but out of scope for this repo to fix.

**`cdiv`'s `assert b != 0` → silent `return 0` change (pattern 5), in `mla.py`,
`mla_swa.py`, and `streamindex_topk.py`.** All three files changed a loud assert into a
silent zero-return for a zero divisor. Checked every call site in all three files: every
one passes `bkv_sz`/`bq_sz`/`static_q_len`-derived divisors, which are always
compile-time-positive block-size constants, never runtime zero. **Currently unreachable
at every existing call site** — flagged per pattern 6 as low priority, but it is still a
textbook instance of the exact anti-pattern this audit targets (a loud failure mode
silently replaced with a plausible-looking wrong answer), so any *new* call site added in
the future should not inherit the silent-zero behavior without re-checking this.

## Finding 5 (REFUTED 2026-07-30, same day — see correction below): Divergent Input Embeddings at Layer 0 Step 0 (PyTorch Input Pipeline Bug)

**Correction note, read this first:** this entire finding was a false positive
caused by a bug in the *comparison script*, not vllm-torchtpu. The checkpoint's
`config.json` has `"hc_mult": 4` (Hyper-Connections) — every dumped hidden-state
tensor is shaped `(num_tokens, hc_mult=4, hidden_size)`, where the size-4 axis
holds 4 *identical* copies of the same token's stream right after the embedding
layer (`vllm/models/deepseek_v4/amd/model.py:564`:
`hidden_states.unsqueeze(-2).repeat(1, self.hc_mult, 1)`), not 4 distinct
tokens. §5.1/§5.2 below mistook this hc-stream axis for a token-block axis;

### 5.1 Parity Stride Layout in JAX sharded blocks (refuted, see correction note above)
During cross-framework bisection of hidden states, we isolated the first divergence at Layer 0. Under attention DP=8 sharding in JAX, sequence blocks are sharded across devices. The gathered global array indexes blocks with a deterministic stride:
* **Prefill (Step 0):** Stride of **16 blocks** (64 tokens) per device. JAX token `d * 64 + t` matches PyTorch token `d * 4 + t` (where `d < 4` is the device and `t < 4` is the token slot).
* **Decode (Step 1):** Stride of **8 blocks** (32 tokens) per device.
Applying this stride mapping confirmed that gathered Layer 0 output hidden states match PyTorch with a Cosine Similarity >`0.996` (nearly `1.0000` for all active tokens).

### 5.2 Input Embedding Corruption in PyTorch (refuted, see correction note above)
At the very beginning of Step 0 (prefill input), JAX and PyTorch input embeddings diverge for tokens 1, 2, and 3:
* **JAX (`tpu-inference`):** Input IDs `[0, 128803, 43651, 2137...]` are correctly embedded into distinct floating-point vectors.
* **PyTorch (`vllm-torchtpu`):** Tokens 1, 2, and 3 are embedded with values **exactly identical** to token 0's embedding (the `<｜begin of sentence｜>` token).
* **Implication:** The tokenizer output is identical (`prompt_token_ids_len=15`), but the parallel embedding layer in PyTorch either receives incorrect input IDs (`[0, 0, 0, 0...]` instead of the token list) or indexes them incorrectly during parallel initialization.
