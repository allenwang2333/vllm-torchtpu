**Date:** 2026-07-27
**Branch:** `patemotter/dsv4-correctness-fixes`

## 1. Why the attention-layer class structure looks the way it does

### 1.1 The forced inheritance switch

At commit `3b5071c0`, `VllmDeepseekV4MLAAttention` inherited directly from `vllm.models.deepseek_v4.attention.DeepseekV4Attention`:

```python
class VllmDeepseekV4MLAAttention(dsv4_attention.DeepseekV4Attention, AttentionLayerBase):
    ...
    super().__init__(vllm_config, prefix=prefix, ...)
```

By the current HEAD (and the currently pinned `vllm==0.23.0`), **this class no longer exists**. Checked directly against the installed package:

```python
from vllm.models.deepseek_v4 import attention as dsv4_attention
'DeepseekV4Attention' in dir(dsv4_attention)  # False
[n for n in dir(dsv4_attention) if 'Attention' in n]
# ['AttentionBackend', 'AttentionLayerBase', 'AttentionMetadata',
#  'DeepseekV4MLAAttention', 'DeepseekV4MultiHeadLatentAttentionWrapper']
```

Upstream vLLM refactored DeepSeek V4 support to split backend-specific attention implementations (AMD/ROCm, NVIDIA/FlashMLA) out of the shared `attention.py` into `vllm.models.deepseek_v4.amd.model` / `.nvidia.flashmla`, keeping only the shared base classes (`DeepseekV4MLAAttention`, `DeepseekV4MultiHeadLatentAttentionWrapper`) in `attention.py`. This is **not** something this codebase chose — it's a consequence of tracking `vllm==0.23.0`. Commits `4d6b9450`/`db30ba1a` switched the base class to `ds_v4_amd_model.DeepseekV4Attention` (the AMD-specific implementation) because that was the only remaining concrete `DeepseekV4Attention` class to wrap:

```python
class VllmDeepseekV4MLAAttention(AttentionLayerBase, ds_v4_amd_model.DeepseekV4Attention):
    ...
    _orig_ds_v4_attention_cls.__init__(self, vllm_config, prefix=prefix, ...)
```

**Implication:** reverting to the old inheritance is not viable without downgrading vLLM. The AMD-class wrapping is the only path forward under the current pin.

### 1.2 Why `self.mla_attn` gets aliased to `self`

The AMD `DeepseekV4Attention.__init__` builds a real composition:

```
outer (DeepseekV4Attention, what we subclass)
 └─ .mla_attn = DeepseekV4MultiHeadLatentAttentionWrapper(...)   # "child"
     └─ .mla_attn = DeepseekV4MLAAttention(...)                  # "grandchild"
```

Both the child and grandchild independently implement `get_kv_cache_spec`, and (per `docs/old_attempts.md` §"Unintended Spec Collection & Missing TPU Padding") both register under the **same prefix** during vLLM's spec-collection walk — the grandchild, being visited last, silently overwrote the parent's TPU-correct spec with an unpadded/GPU-style one. That historical bug was fixed by monkey-patching `get_kv_cache_spec` on both child and grandchild to redirect to the outer object's method (`custom_ops/deepseek_v4.py:876-879`), and — as part of the same effort — collapsing `self.mla_attn` to alias `self` (`self.__dict__['mla_attn'] = self`) so that `self.mla_attn`, `self.mla_attn.mla_attn`, etc. all resolve predictably to one object.

**This collapsing is DSV4-specific, not an established codebase pattern.** Compared against `VllmGatedDeltaNetAttention` in `layers/vllm/custom_ops/gdn_attention_op.py` (Qwen3's GDN attention patch) — that class does plain single inheritance (`class VllmGatedDeltaNetAttention(QwenGatedDeltaNetAttention)`) with a normal `super().__init__()` and no aliasing tricks, because Qwen3's attention class has no such wrapper/grandchild nesting to begin with. DSV4 is the only model in this codebase with this structural complexity, so there was no existing simpler pattern to borrow when this workaround was written.

### 1.3 The side effect this session found and fixed

The `self.mla_attn = self` collapse (`custom_ops/deepseek_v4.py:875`, pre-existing at HEAD) silently discards the only reference to the *real* wrapper object — which is where `swa_cache_layer`, `compressor`, and `indexer` actually live (set in `vllm/models/deepseek_v4/attention.py:227`, `DeepseekV4MultiHeadLatentAttentionWrapper.__init__`). After the collapse, `self.mla_attn.swa_cache_layer` resolves to `self.swa_cache_layer`, which was never set on the outer object — because only `head_dim`, `n_local_heads`, `rotary_emb`, etc. get duplicated onto the outer class by the AMD model's own `__init__`, not the cache/module objects. This is fixed in §2.4 below.

## 2. Bugs found and fixed this session

Investigated in the order discovered, each verified individually (kernel pytest suite and/or a live TPU run) before moving to the next.

### 2.1 `mla.py`: broken output write (the original "garbage token" root cause)

**File:** `src/vllm_torchtpu/kernels/deepseek_v4/mla.py`, `compute_with_bq` (~line 650, pre-fix)
**Symptom this explains:** model runs across all layers, no NaN, no crash — but generates incoherent garbage. Exactly what was reported at `3b5071c0` and by every run since.

An uncommitted, half-finished rewrite (present in the working tree when this session started, layered on top of `3b5071c0`) had replaced the kernel's final output write:

```python
out = lax.div(acc.astype(jnp.float32), L.astype(jnp.float32)).astype(q_dtype)
# ... out was written to bo_x2_ref here, previously
```

with a debug dump of internal softmax bookkeeping instead:

```python
bo_x2_ref[bo_sem_idx, :bq_sz, :, :128]    = l_ref[...]        # was: out
bo_x2_ref[bo_sem_idx, :bq_sz, :, 128:256] = m_ref[...]
bo_x2_ref[bo_sem_idx, :bq_sz, :, 256:512] = acc[..., 256:512] # unnormalized
```

`out` was computed and then never used — confirmed via `grep -n '\bout\b' mla.py`. The kernel's output tensor contained raw `(l, m, acc)` state instead of the real attention result: finite, no crash, but numerically meaningless.

This same uncommitted diff also introduced unfinished `is_static_decode`/`alloc_bq_sz`/`tp_size` batched-decode work (a pre-existing performance TODO, not a correctness requirement) and removed the kernel's `input_output_aliases` block and several `@pl.when(seq_idx == start_seq_idx)`-style sequence-boundary guards (replacing them with `@pl.when(True)`) with no explanation.

**Fix:** `git checkout HEAD -- mla.py` — discarded the entire uncommitted rewrite rather than debug forward from a half-finished state. The batched-decode work can be redone later as a clean, isolated change once the model is verified correct.

### 2.2 `mla.py`: JAX/Pallas Ref-unpacking incompatibility

**File:** `src/vllm_torchtpu/kernels/deepseek_v4/mla.py:538` (post-revert)
**Found via:** `tests/kernels/test_dsv4_mla.py::test_correctness1` (the non-CSA / `kv_lens_to_attend` path)

```
ValueError: Attempting to pass a Ref Ref<smem>{int32[274]} to a primitive: dynamic_slice
-- did you forget to unpack ([...]) the ref?
```

`lax.dynamic_slice_in_dim(kv_lens_to_attend_ref, q_len_start, bq_sz)` was called directly on an SMEM scalar-prefetch `Ref` — invalid without first indexing it. This is a real, JAX-version-sensitive bug (plausibly surfaced by the `main`-branch "Bump JAX to 0.10.2" commit, which this branch is based on), independent of the output-write bug above. The discarded diff from §2.1 happened to also contain the correct fix for this line; it was reapplied on its own after confirming (via the reverted state failing this exact test) that it was necessary.

**Fix:**

```python
slice_lens = jnp.stack([kv_lens_to_attend_ref[q_len_start + i] for i in range(bq_sz)])
```

### 2.3 `mla.py`: `attention_sinks` unsliced broadcast (regression vs. `mla_swa.py`)

**File:** `src/vllm_torchtpu/kernels/deepseek_v4/mla.py:613` (post-revert)
**Found via:** full-model run — `TypeError: sub got incompatible shapes for broadcasting: (64, 1), (8, 128)`

This is the exact shape-mismatch signature documented in `docs/development_log.md` as "Issue #17/#18," previously fixed. At HEAD, `mla.py` had regressed to:

```python
attention_sinks = jnp.concat([attention_sinks_ref[...] for _ in range(bq_sz)])[..., None]
```

— reading the full (padded) `attention_sinks_ref` without first slicing to `num_q_heads`. The sibling file `mla_swa.py` (never touched this session) already had the correct form (`attention_sinks_ref[:num_q_heads]`), confirming this was a `mla.py`-specific regression, not a case where the fix was wrong. `mla.py` has seen far more churn than `mla_swa.py` throughout this effort (per the regression-audit findings below), consistent with it losing a previously-applied fix.

**Fix:**

```python
sinks_clean = attention_sinks_ref[...][:num_q_heads]
attention_sinks = jnp.concat([sinks_clean for _ in range(bq_sz)])[..., None]
```

Verified: `test_dsv4_mla.py` + `test_dsv4_mla_swa.py` (5 tests) still pass after this change.

### 2.4 `custom_ops/deepseek_v4.py`: `self.mla_attn` aliasing destroys cache/module access

**File:** `src/vllm_torchtpu/layers/vllm/custom_ops/deepseek_v4.py:875` (`VllmDeepseekV4MLAAttention.__init__`)
See §1.3 for root cause. This blocked **every layer** from constructing — `_build_attn_op()` (called from `__init__`) reads `self.mla_attn.swa_cache_layer.block_size`, which resolved to a nonexistent attribute and hit the (correct, intentional) "never guess a page size" `RuntimeError` guard.

**Fix:** capture the real wrapper before the alias overwrite, and copy over the attributes that live only on it:

```python
self.custom_prefix = prefix
_real_mla_attn = self.mla_attn
for _attr in ("swa_cache_layer", "compressor", "indexer"):
    if hasattr(_real_mla_attn, _attr) and not hasattr(self, _attr):
        object.__setattr__(self, _attr, getattr(_real_mla_attn, _attr))
self.__dict__['mla_attn'] = self
```

(`object.__setattr__` used deliberately, matching the existing pattern elsewhere in this file, to avoid `nn.Module.__setattr__` re-registering already-registered submodules under `self`.)

### 2.5 `custom_ops/deepseek_v4.py`: unguarded `.kv_cache` reads crash during the profiling pass

**Files/lines:** `VllmDeepseekCompressor.forward` (~line 592) and `VllmDeepseekV4Indexer.forward` (~line 785)
**Found via:** full-model run — `AttributeError: 'VllmDeepseekV4MLAAttention' object has no attribute 'kv_cache'`, raised inside `nn.Module.__getattr__`, during vLLM's pre-allocation memory-profiling forward pass (before any real KV cache tensor is bound).

Both functions read `self.k_cache.kv_cache` (or similar) unconditionally. The **outer** attention layer's own forward path already handles this correctly (`_get_active_sw_cache`/`_get_active_main_cache` at ~line 1118 use `getattr(obj, "kv_cache", None) is not None` guards and fall back to a dummy zero-size cache) — the compressor and indexer forwards never got the same treatment.

**Fix:** early-return (compressor) / return dummy zeros of the shape the fake op expects (indexer) when `getattr(self.k_cache, "kv_cache", None) is None`.

### 2.6 `custom_ops/deepseek_v4.py`: hunk-by-hunk review of the rest of the uncommitted diff

Beyond the swa_cache/kv_cache issues above, the rest of the file's uncommitted diff was reviewed and triaged:

**Kept** (legitimate fixes, left as-is):
- NaN/Inf-safe `dummy_sum` computation in the zero-cache/dead-code-elimination-prevention paths (`_deepseek_v4_attention_jax`) — guards against corrupting an otherwise-clean zero output when summing garbage/uninitialized buffer contents for the XLA-DCE-prevention trick.

The unconditional one risked a shape-mismatch crash on an empty/dummy cache; removed, kept the guarded one.

This directly undoes `docs/dsv4_correctness_fixes.md`'s "Round 2, Fix R2-3," which explicitly made this failure loud because a wrong guessed page size (e.g. 16 vs. the real 64) silently misaddresses every SWA cache slot. Restored the original raise + comment.
- The `tp_size=tp_size` kwarg added to the call into `mla_ragged_paged_attention` (mla.py) — mla.py at HEAD (after §2.1's revert) does not accept this parameter; would have raised `TypeError: unexpected keyword argument`. Removed just this one kwarg (the sibling kwarg into the SWA call is fine, since `mla_swa.py` does accept `tp_size`).

**Kept but flagged for a closer look, not yet independently verified:**
- Non-CSA branch of `max_valid_kv`/`extra` lost its `clamp(min=1)` in the same commit (`4d6b9450`) that introduced the SWA-merge regression fixed in `db30ba1a` — no rationale given, unlike the analogous, well-justified CSA-branch clamp removal in `docs/dsv4_correctness_fixes.md` Fix 3. Left as-is (removing the clamp does match the reference's `topk_len = (pos+1)//COMPRESS_RATIO` with no clamp), but worth a targeted check at position 0 for non-CSA layers if anything still looks off downstream.

### 2.7 `tests/kernels/test_dsv4_compressor.py`: stale reference decode

**File:** `tests/kernels/test_dsv4_compressor.py:132` (`_boundary_store_ref`)
**Found via:** `test_compressor_forward_matches_reference[4-True-8-0-1]` — 87.5% of elements wrong, some off by ~10,000×, others exactly matching (the exact-match subset was the untouched bf16 rope portion, unaffected by the bug).

scale = np.exp2(np.asarray(scale[0]).astype(np.float32) - 127.0)

## 3.5. New finding: narrow, reproducible NaN at the first HCA layer (layer 3)

**Found via:** full 43-layer run with all fixes above applied (plus `VLLM_RPC_TIMEOUT`/`TORCH_DIST_TIMEOUT` extended to survive eager-mode per-layer kernel tracing, since the default 10s `VLLM_RPC_TIMEOUT` was too short and produced a misleading `TimeoutError: RPC call to sample_tokens timed out` that was actually a downstream symptom of this NaN, not a real timeout problem).

Comparing `nan_dump_*.pt` file timestamps against the run's actual timeframe (dumps for layers 0-2 were stale, from earlier runs; fresh dumps exist for every layer 3-16, matching when this run reached each layer) isolates the true origin to **layer 3 — the first HCA layer (`compress_ratio=128`) in the model** (`compress_ratios=[0,0,4,128,...]`: layers 0-1 are SWA-only, layer 2 is the first CSA layer and stayed clean, layer 3 is the first HCA layer and is where NaN first appears). Every layer afterward inherits the corruption via the residual stream — the same investigation into layer 16 initially looked like a fresh bug, but its `q`/`kv` attention-op inputs were already ~94% NaN, i.e. inherited, not generated there.

At the true origin (layer 3):
- `q`/`kv` (the attention op's own inputs, post-RoPE) are **completely clean** — the bug is generated inside this layer's Pallas attention kernel itself, not upstream of it.
- `output` has exactly **240/65536** NaN elements.
- For **every one of the 15 prefill tokens and all 8 heads**, the NaN lands at exactly the same two positions in the 512-wide head vector: **column 10 and column 34** — nowhere else. This is a token/head-independent, purely structural signature.
- This is the very first prefill for a brand-new sequence (`main_kv_lens=[15, 0, 0, ...]`, `main_cu_q_lens=[0, 15]`, single sequence). `extra` (the HCA compressed-window valid length, `(pos+1)//128`) is `0` for every position, which is expected — a `compress_ratio=128` layer legitimately has no compressed-cache contribution yet for a 15-token prefill; the real output should come entirely from the SWA merge.

This matches the class of bug already flagged in `mla.py`'s own comments (~line 457, ~474-479, ~592-595): cache pages that have never been written contain arbitrary/garbage bytes, and certain byte patterns in the fp8/e8m0 packed format decode to NaN (e.g. `float8_e8m0fnu` byte `0xFF`) — which is why the kernel explicitly zero-masks invalid KV before use. The fixed, narrow "always columns 10 and 34" signature suggests that masking has a small gap — two specific byte-lanes in the packed cache layout aren't being caught by whatever guard covers the rest, specifically on a completely unwritten page. Pinpointing the exact line will need `jax.debug.print` instrumentation inside the kernel itself (not just Python-level tensor dumps) and a few rebuild/rerun cycles — not yet done as of this document.

**Not yet investigated further, flagged for the next session:**
- Whether the two-column pattern shifts with `head_dim`/quant-block-size configuration (would confirm the byte-lane theory) or is coincidental.
- Whether this only affects the very first prefill on an unwritten page, or persists once the page has real data (i.e., does regenerating the run with a warm/pre-populated cache avoid it).

## 3.6. Confirmed fix: missing modulo wraparound in compressor block indexing

**Files:** `src/vllm_torchtpu/layers/vllm/custom_ops/deepseek_v4.py` (`_deepseek_v4_compressor_jax`, `state_cache_block_num`/`k_cache_block_num`), `src/vllm_torchtpu/kernels/deepseek_v4/compress_norm_rope.py` (`gather_state_windows`, `flat_index`)

Confirmed via a real diagnostic print (`state_block_tables.shape=(512,)`, `max_num_seqs=64`, `max_num_blocks_per_req=8`, `state_block_size=1`): with `state_block_size=1`, `state_cache_block_num = positions // state_block_size` equals the raw absolute position with no bound. Any position ≥ `max_num_blocks_per_req` (8) aliases into the *next* request's block-table slice — for a single-request batch, that's normally-unused/padding block-table entries, whose contents can reference the same physical page the active request is using, corrupting it. `tests/kernels/test_dsv4_compressor.py`'s own test harness avoids this class of bug entirely by placing state and KV in disjoint page ranges (`kv_base = num_state_pages * PAGE_SIZE`) — the real model has no equivalent separation, relying only on this block-index arithmetic to stay in-bounds, which it didn't.

Fixed by adding `% max_num_blocks_per_req` to keep the within-request block index inside `[0, max_num_blocks_per_req)`, i.e. a true circular/sliding-window buffer as `SlidingWindowMLASpec`'s name implies. Applied to **both** the write side (`state_cache_block_num`, `k_cache_block_num`) and the read side (`gather_state_windows`'s `flat_index`, which had the identical unbounded-division gap) — fixing only one side would have made writes wrap while reads didn't, creating a new mismatch.

**Verified via a full model run**: layers 0-1, previously never clean, are now clean (no NaN dump, no corruption). All 12 kernel tests still pass.

## 3.7. Still open: possible cache-spec allocation mismatch (CSA layers)

Past the fix in §3.6, the NaN origin moves to layer 2 (CSA, `compress_ratio=4`) on a decode step where the CSA masking logic itself checks out (`max_valid_kv` correctly gates `topk_indices` to the 4 valid compressed slots for `position=15`), but reading those slots still produces NaN, and no poison-byte pattern is present at the raw page rows the topk indices would naively index.

Tracing further surfaced a bigger, unresolved architectural question: the compressor's write-side page table (`state_block_tables`, from `VllmCompressorStateCache`'s own `SlidingWindowMLASpec` allocation) and the attention's read-side page table (`main_page_indices`, from the outer layer's `MLAAttentionSpec` allocation) are **two independent vLLM cache-spec allocations** — despite `compressor.k_cache = self` (for `compress_ratio > 1`) implying they reference the *same* physical cache tensor. Whether vLLM's cache manager actually guarantees consistent page numbering across these two independently-allocated specs for a shared-buffer cache group (`unify_hybrid_kv_cache_specs`/`shared_kv_cache_layers` in `tpu_runner.py`) is not yet confirmed — this is the recommended next investigation, and would need tracing vLLM's own cache-manager code rather than further kernel-level dump inspection.

## 3.8. §3.7 hypothesis refuted; real root cause found and partially fixed (session 2)

**§3.7's independent-cache-spec-allocation theory is wrong.** Traced vLLM's own KV-cache-group code (`tpu_runner.py`'s `get_kv_cache_spec`/`initialize_kv_cache`, vLLM's `kv_cache_utils.py`) and confirmed the DSV4-specific allocator (`_get_kv_cache_config_deepseek_v4`) does keep `num_blocks` uniform across the full-MLA group and the SWA/state-cache groups by design — and separately, `forward_mqa` (`custom_ops/deepseek_v4.py`) already resolves `main_attn_metadata` via `attn_ctx.get(compressor_state_prefix) or attn_ctx.get(main_layer_name) or ...`, i.e. it deliberately tries the compressor's own metadata *first* for the main attention read too. A live diagnostic print at the real (non-profiling) forward pass confirmed `attn_ctx[compressor_state_prefix] is attn_ctx[main_layer_name]` (literal same Python object, not just equal) for both layer 2 (CSA) and layer 3 (HCA). This matches `dsv4_correctness_fixes.md`'s earlier "Verified-correct areas" note on the shared state/KV buffer, which this session's own §3.7 had contradicted without citing it. **Conclusion: don't re-open this path; the block tables are synchronized by construction.**

**Real root cause (confirmed via fresh dump + fix, verified against kernel tests):** `mla.py`'s and `mla_swa.py`'s `flash_attention` inner functions correctly zero the attention-weight `p` at masked/invalid key positions (`p = jnp.where(mask, 0.0, ...)`), but never sanitize the raw `kv` values before `pv = jnp.einsum("nm,md->nd", p, kv, ...)`. In IEEE-754, `0.0 * NaN == NaN`, so any `kv` row that's still poison bytes from a never-written cache page (confirmed: `0x7F`/`0xFF` bytes in `main_cache_kv`, decoding to NaN under fp8) corrupts the reduction at that column for *every* query in the block, regardless of the zero weight. Symptom matched exactly: on a first-15-token HCA prefill (`extra`/`kv_lens_to_attend` = 0 everywhere, i.e. nothing should be read from the compressed cache at all yet), one deterministic output column was NaN across every token and every head.

**Fix applied** (both `mla.py` line ~210 and `mla_swa.py` line ~191, same pattern): compute `row_invalid = jnp.all(mask, axis=0)` (a key row masked out for *every* query in the block — safe to zero regardless of garbage content, since no query actually needs it), then zero those `kv` rows before the `pv` einsum:

```python
row_invalid = jnp.all(mask, axis=0)
row_scale = jnp.where(row_invalid, 0.0, 1.0).astype(kv.dtype)
kv_clean = kv * row_scale[:, None]
pv = jnp.einsum("nm,md->nd", p, kv_clean, preferred_element_type=jnp.float32)
```

**Mosaic gotcha:** the first attempt used `jnp.where(row_invalid[:, None], 0.0, kv)`, reshaping the *boolean* `row_invalid` directly — this fails to compile (`MosaicError: unsupported shape cast`, `vector<16xi1> -> vector<16x1xi1>`). Mosaic doesn't support adding a trailing axis to an i1 (boolean) vector. Fix: only ever reshape/broadcast a float-dtype array; use the boolean only as a same-shape `jnp.where` condition (no reshape needed there), cast to `kv.dtype` first, *then* do the `[:, None]` broadcast.

Verified: all 12 kernel tests still pass with both fixes. `mla_swa.py` needed the identical fix independently discovered — a first full-model run with only `mla.py` patched still showed NaN (now at both layers 2 and 3), because CSA/HCA layers share one physical cache buffer between the SWA kernel and the main kernel (`two_caches_same_buffer`), so the SWA kernel's own unguarded `pv` einsum was reading the same poisoned pages via its own separate vulnerability.

**New, deeper issue found past these fixes — not yet fixed:** a decode-step dump (`position=15` filled in, `main_kv_lens=16`) showed `q`/`kv` (this layer's own inputs) *already* NaN — meaning corruption now originates upstream via the residual stream, not fresh in this layer's kernel. `main_cache_kv` page 0 went from 15 stray poison bytes (prefill-only dump) to **1024 bytes across all 64 rows** — a fully-corrupted page, not scattered garbage, consistent with a real *write* corrupting it rather than unwritten memory being read. This matches `dsv4_correctness_fixes.md`'s previously-flagged-but-never-fixed gap #5: *"Sequence-start state overlap: in the shared buffer, compressed rows written to the entry-0 page can clobber stale state chunks for positions < ~12... worth an audit for tiny-prompt decode."* The compressor writes its per-token "state" (lightning-indexer bookkeeping) into the shared buffer on **every** token unconditionally (regardless of `compress_ratio` boundary), and this now looks like an active bug, not just a theoretical risk: the state write for a new decode token appears to land on rows the SWA/main attention read path expects to hold real K/V bytes.

**Recommended next investigation:** trace the exact offset math in `_deepseek_v4_compressor_jax`'s `_compressor_local` (the state `slot_mapping` write) versus wherever the SWA cache's real K/V write lands in the shared buffer, to confirm the overlap and find the right fix — likely needs genuine row/offset separation between "state" rows and "real KV" rows for small position values, or gating the state write differently. This is a write-side aliasing bug, not a masking gap, so the read-side fixes in this section can't address it.

## 3.9. Confirmed and fixed (session 3): compressor state/real-KV collision, two independent bugs

Traced the §3.8 write-side aliasing lead to completion. Two separate, compounding bugs, both in `custom_ops/deepseek_v4.py`'s `VllmCompressorStateCache`:

**Bug 1 — wrong `block_size`.** `VllmCompressorStateCache.__init__` recomputed `self.block_size` from `cache_config.block_size // compress_ratio // 4 // 2 // coff`, overriding the value the vLLM base class (`vllm.models.deepseek_v4.compressor.CompressorStateCache.__init__`) already sets correctly (`4` for CSA, `8` for HCA — see its own comment deriving this from the exact packed-cache row geometry, `[64, 584]` KV block shape). The override produced `1` for both CSA and HCA. With `state_block_size=1`, one compressor-state token occupies an *entire* physical page (`page_size // 1` = 64 rows) instead of the intended 16 (CSA) / 8 (HCA) rows. Confirmed the same broken formula exists in `tpu-inference`'s (the sibling JAX-native repo, `~/workspace/tpu-inference`) own `VllmCompressorStateCache` — likely copy-pasted from a shared ancestor and never actually exercised there. **Fix:** deleted the override; keep the base class's value.

**Bug 2 — state and real/compressed-KV sharing one physical buffer at all.** Even with `block_size` fixed, state writes and compressed-KV writes both indexed into the *same* physical tensor (`compressor.k_cache.kv_cache`, deliberately aliased to the outer attention layer's own KV cache via `object.__setattr__(self.mla_attn.compressor, "k_cache", self.mla_attn.mla_attn)`, `custom_ops/deepseek_v4.py:926-930`) — a TPU-specific memory-saving optimization not present in the upstream CUDA/AMD path (there, `state_cache.kv_cache` and `k_cache.kv_cache`/`kv_cache` are two independently-allocated tensors; see `vllm.models.deepseek_v4.compressor.DeepseekCompressor.forward`). Confirmed via a live diagnostic print that `self.mla_attn.compressor.state_cache.kv_cache` *is* already a genuinely separate, independently-allocated tensor (`is_same_as_k_cache=False`, own shape/pages) — vLLM's cache manager was already doing the right thing; the code just never used that buffer, using the shared main buffer for both roles instead.

A second, related discovery: that dedicated `state_cache.kv_cache` tensor was binding with dtype `float8_e4m3fn` instead of the declared `float32` — `vllm_torchtpu/kv_cache_spec_normalizer.py`'s `_normalize_one_spec` force-overrides *every* KV-cache spec's dtype to the model's global quantization dtype *unless* the spec already declares `torch.uint8` (the deliberate escape hatch the shared MLA/SWA buffers already use). Storing raw (pre-quantization) state floats into an fp8 buffer would have silently wrecked precision.

**Fix (mirrors the reference `tpu-inference` implementation's two-metadata-source pattern, `layers/vllm/custom_ops/experimental/deepseek_v4/deepseek_v4_compressor.py`):**
- `VllmCompressorStateCache.get_kv_cache_spec`: declare `dtype=torch.uint8` (not float32) and `head_size=align_to(bytes_per_row, 128)` (not `state_dim`) — reusing the exact same packed-byte-lane convention (`pack_state_cache`/`unpack_state_cache` in `compress_norm_rope.py`) the shared buffer already uses, just against this disjoint tensor.
- `_deepseek_v4_compressor_jax`: now takes `state_cache_buf` (dedicated) and `cache` (shared main buffer) as two separate array arguments, plus `k_block_tables` as a separate block table from `state_block_tables` — the compressed-KV `kv_slot_mapping` must address the *main* buffer's own page-table space (matching `main_page_indices`), not the state buffer's. Returns `(updated_cache, updated_state_cache_buf)`.
- `compressor_forward`/`compressor_forward_indexer` (`kernels/deepseek_v4/compressor.py`): same split — `unpack_state_cache`/`pack_state_cache` now operate on `state_cache_buf`; `compress_norm_rope_store(_indexer)`'s final write still targets `cache` (unchanged internally, since it already took `cache` and a separately-unpacked f32 `state_view` as distinct params).
- `VllmDeepseekCompressor.forward`: fetches `state_cache_buf = self.state_cache.kv_cache` and a separate `k_cache_metadata` (via `self.k_cache.prefix`) for `k_block_tables`; writes back both updated tensors.
- `tests/kernels/test_dsv4_compressor.py`: updated to construct two separate small uint8 tensors instead of one combined-with-offset tensor, and to unpack the new `(cache, state_cache_buf)` tuple return.

**Verified:** all 12 kernel tests pass. Full 43-layer real-checkpoint run: **zero NaN detections across the entire run** (previously NaN by layer 3 every time), no crash, no `EngineDeadError`. First-token logprobs are sane (`I`, `The`, `好的`, `Here` as top-5 candidates — a plausible chat-response distribution). Generated text is still garbled after the first token (`the the the the the Irregularity = ...`), but this is a qualitatively different, more ordinary symptom than the NaN/crash chain this session was chasing — see §5 for the next lead.

**Three confirmed regressions found and fixed**, each verified by (a) diffing against `tpu-inference`'s working code and (b) tracing to a specific vllm_torchtpu commit whose stated rationale doesn't cover the actual change made:

1. **`custom_ops/deepseek_v4.py`, `forward_mqa`: HCA `main_kv_lens` divisor.** The reference computes `main_kv_lens = main_attn_metadata.seq_lens // self.compress_ratio` unconditionally, for both CSA (`compress_ratio=4`) and HCA (`compress_ratio=128`) layers. 2. **`custom_ops/deepseek_v4.py`, `_deepseek_v4_attention_jax`: `two_caches_same_buffer` gate.** The reference does `if two_caches_same_buffer: main_cache_kv = updated_sw_cache` with no `is_csa` condition. 3. **`kernels/deepseek_v4/streamindex_topk.py`, `_fetch_bkv`: missing page-index bounds clamp.** The reference clamps both the logical page-table index (`jnp.minimum(page_indices_offset + i, num_page_indices - 1)`) and the resulting physical HBM page offset before the DMA copy that fetches indexer KV pages for CSA top-k scoring; vllm_torchtpu had no such clamp at all (not a regression — appears to have simply never been added). Fixed: added the identical clamp.

**A methodological finding along the way, worth keeping in mind for any future MXFP4 test:** the first version of this test compared `apply_monolithic`'s output against a reference computed from the *pre-quantization* float weights, with a 20% tolerance — and failed, with up to 47% of output elements exceeding tolerance and relative errors as high as 180%. This looked alarming, but root-caused (via `scratch/debug_dequant_check.py` and `scratch/debug_full_reference_check.py`, not kept) to two things, neither a real bug:
1. MXFP4's e2m1 grid (`{0, 0.5, 1, 1.5, 2, 3, 4, 6}` per sign, only 8 magnitude levels) is genuinely very lossy for literal `torch.randn` weights — gaps between adjacent grid points reach 2.0 near the top of the range, so per-element round-trip quantization noise on random Gaussian data is large by construction, not a sign of a bug.
2. `process_weights_after_loading`'s second quantization stage (dequantize checkpoint format → requantize for the internal GMM kernel format) is a confirmed **exact no-op** on already-once-quantized values (verified directly: requantizing stage-1-dequantized weights at the same block size reproduces them bit-for-bit) — so the "double quantization" compounding-error theory doesn't apply either.

The fix was building the reference from the **dequantized** checkpoint weights (what `process_weights_after_loading` itself produces from the real quantized input) rather than the pre-quantization float ground truth — this isolates whether the actual routing/GMM/activation computation is correct, without conflating it with MXFP4's inherent (and unavoidable, real-checkpoint) lossiness. With that fix, both tests pass tightly (atol=rtol=6e-2, kernel-level bf16 precision, no quantization noise left to explain).

A second, smaller bug was in the hash-routing test's own reference (not vllm_torchtpu): `select_experts`'s non-grouped path always renormalizes `topk_weights`, which — with `top_k=1` (realistic for hash-MoE) — collapses every weight to exactly `1.0` regardless of the underlying gating score. The test's first reference implementation omitted this renormalization step, comparing against the raw (small) gating score instead of `1.0`, again producing large, bug-looking errors that were actually a reference bug. Verified directly via a side-by-side dump of `select_experts`'s real output against the manual computation before and after adding the renormalize step.

**Both tests confirmed passing together with the full 27-test standard suite (30 total, no regressions).**

**Investigation implication: this rules out MoE dequant+GMM+routing as the garbled-text root cause, closing §3.12's item (1) with a negative result — the coverage gap is closed, but the root cause is still unfound.** Combined with the four confirmed-and-fixed regressions in §3.10-3.12 (none of which changed the full-model output at all) and `mla_swa.py`'s 32/50-step clean stress test (§3.11), the surface area of components independently verified correct against a trusted reference is now large. **Major finding: this repo's `vllm==0.23.0` pin is not reproducible, and a second, larger incompatibility exists that was never fixed.** While setting up a native `uv` venv (the Docker image this whole investigation has run against, `vllm-torchtpu-local:latest`, disappeared mid-session — untagged/removed by an unknown process, not this session's doing), a real full-model run hit a hard crash *distinct from and beyond* the MRO issue: `AttributeError: 'VllmDeepseekV4MLAAttention' object has no attribute 'mla_attn'`. **Deliberately NOT fixed this session** — decided with the user not to chase this: the garbled-text investigation this whole branch is built on has only ever been validated against whatever (older) vLLM commit is baked into the missing Docker image. Fixing the flattened-structure incompatibility would get the model running against a *different, never-before-validated* vLLM build, making any observed behavior (garbled or not) incomparable to six sessions of prior findings, and risks introducing new bugs while reworking code the whole architecture narrative depends on. **Decision: restore Docker access (retry pulling `us-central1-docker.pkg.dev/cloud-tpu-inference-test/vllm-tpu-rdna/vllm-torchtpu-patemotter_google_com:latest`, possibly needs `gcloud auth configure-docker us-central1-docker.pkg.dev` first) and keep using that exact environment for full-model runs and the garbled-text investigation specifically. **Environment gotchas found and fixed this session, for the next person setting up a native venv**: two root-owned leftover directories from prior Docker-based work blocked native (non-root) builds/runs — `src/vllm_torchtpu.egg-info` (blocked `uv pip install -e .`) and `/dev/shm/torch_tpu_cache` (blocked TPU compilation, crashing with `Check failed: lock_fd_.valid() ...
