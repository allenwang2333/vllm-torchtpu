DeepSeek-V4 KV cache: logical caches and physical allocation

DSv4 declares far more logical caches than it allocates arrays. Sliding-window caches and compressor state caches carry no memory of their own; they are bound onto an array another layer already owns, at offset 0. Nothing in the bytes separates them. The allocator keeps them apart by never handing one block ID to two cache groups.

1What each layer declares

A three-layer slice: two CSA layers and one HCA layer. Filled marks allocate; dashed marks are overlaid onto someone else's array. Real DeepSeek-V4-Flash has 21 CSA layers and 43 SWA layers (tpu_runner.py:5797-5799).

2Where those caches physically live

Seven arrays for eleven logical caches. The first card is the interesting one: four caches from four different cache groups share it, at the same byte offset.

_validate_ds_v4_overlay enforces the one thing checkable from geometry alone: two layers of the same group may never land on one array, because they share a block table. Cross-group sharing is legal and is what the first card shows.

The overlay depends on how vLLM groups the layers, which the runner logs for exactly that reason (tpu_runner.py:5833-5848). Drawn here is the grouping the Raiden fixture models (tests/distributed/raiden_test_utils.py:174-190): all SWA layers in one group, so they take hosts 0, 1, 2 in turn. If vLLM instead puts every SWA layer in its own group, each is at position 0 and they all land on the first CSA NoPE array. With more overlay consumers than CSA arrays, _host_at allocates fresh ds_v4_overflow.i arrays rather than double-book a same-group array.

3What keeps the four apart: block IDs

All groups draw pages from one shared BlockPool, and a block ID is owned by at most one group at a time. That is a runtime invariant, not a property of the layout, so Raiden cannot read it off the arrays.

This is why every DSv4 pool tag carries a .g{ordinal} suffix and why every transfer registers spans against its own group's block table. A tag that did not name the group would address the wrong cache's pages. The ordinal is whatever vLLM's grouping produces; in the DeepSeek-V4-Flash run the SWA group came out as group 1, hence the tag dsv4.swa.g1.

4Page geometry per role

Every role disagrees about how many logical tokens sit on a page and how many rows a token costs. That is why the layout fingerprint records geometry per tag rather than one page_tokens, and why lower_dsv4_row_spans rounds a partial tail page up in rows rather than tokens.

SWA's own page is 128 tokens x 1024 B = 131072 B, byte-for-byte the CSA NoPE page, which is what lets it be overlaid there. Compressor-state block sizes are derived by the kernel layout model rather than a closed form (deepseek_v4_compressor.py:266-309); at ratio 4 / head_dim 512 / block 1024 it comes out 16 (tests/layers/vllm/test_dsv4_compressor_op.py:45-58).
